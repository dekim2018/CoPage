# 13. 테스트와 검증

이 프로젝트의 버그는 "가끔, 특정 순서로 겹칠 때만" 나타난다. 사람이 사례를 생각해 적는 테스트로는 잡을 수 없어서, 무작위로 대량 생성한 상황에서 "모두 같은 결과가 되었는가"를 검사하는 방식을 중심에 둔다.

## 13.1 테스트 단계

| 단계 | 대상 | 방법 | 통과 기준 |
| --- | --- | --- | --- |
| 속성 테스트 | `ot-core` 변환 함수 | 무작위 문서 S와 무작위 연산 a, b를 만들어, a 뒤에 변환된 b를 적용한 결과와 b 뒤에 변환된 a를 적용한 결과를 비교 | 항상 같다 (TP1) |
| 속성 테스트 | 합성, 역연산 | 합성한 연산을 한 번 적용한 결과와 차례로 적용한 결과 비교. 연산 뒤 역연산을 적용하면 원래 문서 | 항상 같다 |
| 수렴 시뮬레이션 | 서버 세션 로직 + 클라이언트 상태 기계 | 가짜 네트워크로 클라이언트 2~8개를 연결하고, 편집, 지연, 순서 뒤바뀜 없는 단절, 재접속을 무작위로 섞어 실행. 끝나면 모든 메시지를 흘려보낸 뒤 비교 | 모든 클라이언트 문서 = 서버 문서 = 로그를 처음부터 적용한 문서 |
| 적합성 벡터 | Java 구현과 TypeScript 구현의 일치 | Java 쪽에서 (문서, a, b, 변환 결과, 적용 결과)를 JSON 파일로 1만 건 내보내고 Vitest가 같은 입력으로 계산해 비교 | 전부 같다 |
| 통합 테스트 | 커밋, 멱등성, 권한, 리스 | Testcontainers로 PostgreSQL과 Redis를 띄우고 실제 WebSocket으로 검사 | 사례별 단언 |
| 화면 테스트 | 편집기 어댑터 | Playwright로 브라우저 두 개를 띄워 동시 입력, Enter와 Backspace 겹침, 한글 조합 중 원격 편집 | 두 화면의 문서가 같다 |

실패한 무작위 사례는 시드 값을 로그에 남겨 그대로 다시 실행할 수 있게 한다. 한 번 발견한 사례는 고정 테스트로 옮겨 다시 생기지 않게 한다.

## 13.2 장애 실험

| 실험 | 방법 | 통과 기준 |
| --- | --- | --- |
| 소유 노드 강제 종료 | 편집 부하 중 `docker kill` | ack 받은 묶음이 전부 로그에 있다. 클라이언트가 10초 안에 편집을 재개한다. 최종 문서가 모두 같다 |
| 노드 일시 정지 | 소유 노드에 `docker pause` 10초 후 `unpause` (리스 6초보다 길게) | 깨어난 노드의 커밋이 유일 제약으로 실패하고 세션을 버린다. 로그에 같은 리비전이 두 개 없다 |
| 노드 추가 | 편집 부하 중 노드를 2대에서 3대로 | 양도된 문서의 클라이언트가 재접속 한 번으로 이어서 편집한다. 유실 0건 |
| DB 지연 | `tc netem` 으로 PostgreSQL 응답에 200ms 지연 | 묶음 커밋으로 처리량이 유지된다. ack 없는 묶음이 남에게 보이지 않는다 |
| Redis 중단 | Redis 컨테이너 정지 30초 | 이미 열린 문서의 편집은 리스 연장이 실패한 시점부터 멈추고(읽기 전용), 복구 후 재개된다. 두 노드가 동시에 쓰는 일은 없다 |
| 클라이언트 단절 | 전송 직후와 ack 직전에 연결을 끊는 프록시를 사이에 둔다 | 같은 묶음이 두 번 적용되지 않는다. 빠지는 묶음도 없다 |
| 느린 클라이언트 | 한 연결의 수신을 멈춤 | 그 연결만 4011로 끊긴다. 다른 사람의 ack 지연이 늘지 않는다 |

실험 스크립트는 `scripts/chaos/` 에 두고, 결과는 `docs/CHAOS.md` 에 표로 남긴다. 팬파라이브와 같은 형식이다.

## 13.3 부하 측정

`loadgen` 의 가상 클라이언트는 실제 클라이언트와 같은 상태 기계를 돌린다. 타이핑 속도(초당 5타)와 Enter, Backspace, 블록 이동의 비율을 시나리오로 정한다.

| 시나리오 | 구성 | 보는 것 |
| --- | --- | --- |
| 한 문서 집중 | 문서 1개에 편집자 10, 25, 50, 100명 | ack 지연, 변환 횟수, 거부율이 인원에 따라 어떻게 늘어나는지 |
| 여러 문서 분산 | 문서 500개에 편집자 2~4명씩 | 노드 1대의 메모리와 CPU, 문서 세션 1개당 메모리 |
| 문서 열기 | 블록 100, 1,000, 5,000개 문서를 스냅샷 간격 50, 200, 1,000으로 | 열기 시간과 저장 용량의 교환 관계 |
| 커밋 방식 비교 | 묶음마다 커밋과 묶음 커밋 | 초당 확정 묶음 수, ack p99 |
| 재접속 몰림 | 노드 종료 후 클라이언트 1,000개가 동시에 재접속 | 복구 시간, 백오프의 무작위 지연이 효과가 있는지 |

## 13.4 남길 지표

운영 중에도 같은 지표를 Micrometer로 내보낸다. 목표값은 1.4의 성공 기준과 같다.

| 지표 | 이름 | 보는 이유 |
| --- | --- | --- |
| ack 지연 | `collab.ack.latency` (p50, p95, p99) | 사용자가 느끼는 저장 속도 |
| 묶음당 변환 횟수 | `collab.transform.count` | 동시 편집이 얼마나 겹치는지. 클수록 클라이언트의 기준 리비전이 뒤처져 있다는 뜻 |
| 거부율 | `collab.nack.rate` (사유별) | 6.6의 거부 규칙이 실제로 얼마나 자주 사용자 입력을 되돌리는지 |
| 커밋 묶음 크기 | `collab.commit.batch.size` | 묶음 커밋이 동작하는지 |
| 열린 세션, 연결 수 | `collab.sessions`, `collab.connections` | 노드 수용량 |
| 세션 복구 시간 | `collab.session.load` | 스냅샷 간격 조정 근거 |
| 리스 충돌 | `collab.lease.conflict` | 두 노드가 겹친 횟수. 0에 가까워야 한다 |
| 연산 크기 | `collab.op.bytes` | 저장 용량 예측 |
