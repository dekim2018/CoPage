# 성능 진단 결과

아키텍처 진단의 성능 항목(PERF-1, PERF-2)과 4단계 부하 시험의 측정값이다. 모든 값은 노트북 한 대에서 잰 것이다. 운영 환경의 값이 아니다. 해석할 때 6장의 주의 사항을 먼저 본다.

## 1. 측정 방법

### 1.1 환경

| 항목 | 값 |
| --- | --- |
| 기기 | Apple 노트북 한 대(M1 Pro, 10코어) |
| 배치 | 서버와 loadgen 이 같은 기기. 네트워크 지연이 거의 없다 |
| 서버 | `java -Xmx1g -jar app/build/libs/app-0.1.0-SNAPSHOT.jar --spring.profiles.active=dev` (힙 1GB, dev 프로필) |
| 저장소 | PostgreSQL 17, Redis 7 을 Docker Desktop 에서(저장소 루트의 `compose.yaml`) |
| 화면 측정 | Node 22, `npm run perf` |

### 1.2 부하 도구 `loadgen`

- 실행: `./gradlew :loadgen:run --args="scenario=... "`(#72)
- 가상 편집자는 ot-core 의 `ClientSession` 을 그대로 써서 브라우저 클라이언트와 같은 규칙으로 맞춘다
- 묶음은 하나씩, 50ms 에 많아야 하나 보낸다(D-34, 브라우저와 같다)
- 누름은 글자 84%, Enter(블록 나누기) 8%, Backspace 8%. 들어오면 자기 문단을 하나 만들고 그 안에서 친다
- 재는 것
  - ack 지연: 보낸 때부터 ack 를 받은 때까지(클라이언트 쪽)
  - 남에게 닿는 지연(remote): 보낸 때부터 다른 편집자가 그 change 를 받은 때까지
  - nack 수, 종료 코드
  - 수렴: 끝난 뒤 모든 편집자의 문서가 같은지
  - 서버 지표(관리 포트): ack 처리 시간(`collab.ack.latency`, 받음부터 ack 까지, 커밋 포함), 커밋 묶음 크기, 세션, 연결, 힙

## 2. 측정값

### 2.1 한 문서 집중

한 문서에 편집자 N 명, 편집자마다 초당 5타, 60초(10명은 30초).

PERF-2(D-38) 전:

| 편집자 | 묶음 | nack | ack p50 / p95 / p99 | remote p99 | 서버 ack 평균 | 수렴 |
| --- | --- | --- | --- | --- | --- | --- |
| 10 | 1,510 | 0 | 3.7 / 8.6 / 14.5 ms | 14.2 ms | 3.3 ms | 예 |
| 25 | 7,526 | 0 | 3.0 / 7.9 / 13.8 ms | 13.8 ms | 2.9 ms | 예 |
| 50 | 15,050 | 0 | 3.3 / 9.3 / 13.0 ms | 13.0 ms | 3.0 ms | 예 |
| 100 | 30,102 | 0 | 11.6 / 75.6 / 125.8 ms | 125.4 ms | 16.0 ms | 예 (커밋 묶음 크기 최대 51) |

PERF-2 뒤:

| 편집자 | ack p50 / p95 / p99 | remote p50 / p95 / p99 | 서버 ack 평균 | nack | 수렴 |
| --- | --- | --- | --- | --- | --- |
| 50 | 1.9 / 5.9 / 9.1 ms | 1.9 / 5.9 / 9.3 ms | 1.59 ms | 0 | 예 |
| 100 | 3.5 / 17.1 / 47.2 ms | 3.5 / 17.1 / 46.2 ms | 3.53 ms | 0 | 예 |

100명에서 PERF-2 전에 지연이 크게 오른 것은 커밋 하나가 묶음 수에 비례해 DB 를 왕복했기 때문이다(4.2). 묶음이 많이 쌓일수록 커밋이 길어지고, 그동안 더 쌓인다.

### 2.3 문서 열기

블록 2,000개 문서. 채운 뒤 세션이 내려갈 때까지 기다려(cold) 첫 열기가 저장소에서 복구하게 했다.

| 항목 | 값 |
| --- | --- |
| 첫 열기(접속부터 welcome 까지, 복구 포함) | 93 ms |
| 서버 세션 복구(`collab.session.load`) | 45.8 ms |
| 이어지는 열기(세션이 메모리에 있음), n=19 | p50 13.3 ms, p95 25.5 ms |

세션을 내릴 때 스냅샷을 남기므로 이 첫 열기는 스냅샷 뒤 연산이 없는 경우다. 1.4 의 조건(스냅샷 뒤 연산 200개)은 맞추지 않았다.

### 2.4 장애 중 성능

자세한 방법과 표는 [docs/CHAOS.md](../CHAOS.md) 에 있다.

| 실험 | 결과 |
| --- | --- |
| 노드 `kill -9` 와 재접속, 연결 20 / 300 / 1,000 | 모두 이어 붙음, ack 받은 묶음 유실 0, 끊김부터 첫 ack 까지 p99 5.8 / 4.4 / 6.3 초. 서버 시작 3.3~4.0 초 포함 |
| DB 지연(Toxiproxy 로 PostgreSQL 응답마다 +200ms, 4명 x 15번) | PERF-2 전 30.4초(초당 2.0 묶음), 뒤 7.0초(초당 8.6) |
| 느린 클라이언트(한 연결이 읽기를 멈춤, 남이 60KB 편집 80번) | 다른 사람의 ack 최대 27 ms, remote 최대 37 ms. 멈춘 연결만 끊겼다 |

DB 지연 실험의 PERF-2 전 값은 CHAOS.md 표에 30.6초로, D-38 과 PR #78 에 30.4초로 적혀 있다. 같은 시험을 따로 돌린 두 번의 값이다. 이 문서는 PR #78 의 비교 값(30.4초)을 쓴다.

### 2.5 검색 (D-47, D-48)

PostgreSQL 17(로컬 compose)에 페이지 10,000 개를 넣고(본문 평균 919자, 낱말 30개를 무작위로 이은 글) 검색 질의를 `EXPLAIN ANALYZE` 로 쟀다. 측정용 데이터는 한 트랜잭션에서 넣고 되돌렸다. 낱말이 30개뿐이라 흔한 낱말은 거의 모든 페이지에 들어 있다(실제보다 나쁜 조건).

| 검색어 | 처음 질의(제목 OR 본문) | 고친 질의(제목과 본문을 따로 찾아 합침) | 인덱스 |
| --- | --- | --- | --- |
| 없는 네 글자 | 185ms | 8.6ms | 본문 pg_trgm 인덱스 |
| 없는 두 글자 | (재지 않음) | 177ms | 쓰지 못함(세 글자 조각이 없다) |
| 거의 모든 페이지에 든 두 글자 | 290ms | 342ms | 쓰지 못함 |
| 거의 모든 페이지에 든 세 글자 | 350ms | 342ms | 본문 인덱스를 쓰지만 모두 맞아 다시 확인한다 |

- 처음 질의는 두 표(pages, page_search)에 걸친 OR 라 인덱스를 전혀 쓰지 못하고 다 훑었다. 제목과 본문을 따로 찾아 UNION 으로 합치게 고쳤다
- 두 글자 이하 검색어는 pg_trgm 으로 거를 수 없어 다 훑는다. 페이지 10,000 개(본문 9MB)에서 약 0.2초다. 이보다 크면 pg_bigm 으로 옮긴다(ADR 0007 덧붙임)
- 많이 맞는 검색어는 맞는 페이지를 모두 정렬한 뒤 200개를 자르므로 맞는 수에 비례한다. 결과마다 권한을 계산하는 비용(후보 200개)은 따로 재지 않았다

### 2.6 연산 로그 크기와 용량

로컬 DB 에 쌓인 시험과 `loadgen` 데이터(문서 2,659개, 연산 행 491,325개)로 쟀다.

| 항목 | 값 |
| --- | --- |
| 연산 행 하나(`doc_ops`, 인덱스 포함) | 388 바이트 |
| 행의 연산 JSON | 평균 132 바이트, 중앙값 125, p99 210 |
| 행 하나의 연산 수 | 평균 1.01 |
| 스냅샷 행 하나 | 평균 1,390 바이트(이 데이터의 문서는 작다) |

계산: 한 사람이 쉬지 않고 칠 때 화면은 50ms 마다 묶어 보낸다(D-34). 묶음 하나가 행 하나이므로 많아야 초당 20행, 시간당 72,000행, 약 28MB 다. 실제 편집은 쉬는 시간이 길어 이보다 훨씬 적다. 디스크 30GB 서버에서 데이터에 20GB 를 쓰면 약 5,000만 행, 쉬지 않고 친 시간으로 700시간이다. 로그는 지우지 않는다(버전 기록이 리비전을 가리킨다, D-44). 그 전에 오래된 로그를 스냅샷으로 접는 작업이 필요하다(하지 않았다).

### 2.7 스냅샷 간격 (D-51)

세션을 정상으로 내리면 그때 스냅샷을 남기므로, 스냅샷 뒤 연산을 다시 적용하는 것은 서버가 갑자기 죽은 뒤 처음 열 때다. 간격이 N 이면 그때 다시 적용하는 연산은 많아야 N 개다. 블록 2,000 개 문서에 한 글자 넣기 연산을 K 개 쌓고 실제 PostgreSQL 로 열었다(`SnapshotIntervalBench`, 7번씩, 중앙값).

| 스냅샷 뒤 연산 K | 열기 중앙값 | 최대 |
| --- | --- | --- |
| 0 | 31.6ms | 69.6ms |
| 50 | 24.2ms | 31.2ms |
| 200 | 28.4ms | 53.0ms |
| 1,000 | 64.5ms | 73.4ms |
| 5,000 | 231.5ms | 245.9ms |

스냅샷 하나를 남기는 데 53.5ms(최대 88.4ms), 크기 26KB 다. 스냅샷은 그 문서의 실행 흐름에서 남기므로 그동안 그 문서의 ack 가 늦는다. 간격 200 에서는 다시 적용이 거의 공짜이고(200 개까지 차이가 재는 흔들림 안), 스냅샷은 묶음 200 개에 한 번(0.5%)이라 ack p99 에 들지 않는다. 간격을 1,000 으로 늘리면 스냅샷 비용은 5분의 1 이 되지만 죽은 뒤 열기가 30ms 남짓 늘어난다. 지금 값(200)을 그대로 둔다.

### 2.8 노드 둘 (D-51)

`deploy/cluster` 로 nginx 뒤에 노드 둘을 띄우고 같은 시험을 노드 하나(node2 를 내림)와 비교했다. 모두 같은 노트북 안이라 노드를 늘려도 CPU 가 늘지 않는다. 늘어나는 처리량이 아니라 노드 사이 비용(소유 리스, 문서별 라우팅)을 보는 측정이다.

| 시험 | 노드 하나 | 노드 둘 |
| --- | --- | --- |
| 문서 100 개 x 3명, 초당 2번 | ack p99 17.3ms, 100/100 수렴 | ack p99 14.4ms, 17.0ms(두 번), 100/100 수렴 |
| 문서 1개 x 50명, 초당 5번 | ack p99 15.6ms | ack p99 17.9ms, 19.3ms |

노드 사이 비용은 재는 흔들림 안이다. 찾은 것: nginx 의 기본 `worker_connections`(512)로는 편집자 300 명에서 연결이 끊겼다(웹소켓 하나가 연결 둘을 쓴다). 실험 구성을 8,192 로 올렸다. 운영 구성(Caddy)에는 이런 낮은 기본 한도가 없다. 노드 둘의 첫 실행은 p99 69.5ms 였는데 막 뜬 node2 가 데워지지 않은 탓으로 보고(같은 시험의 다음 실행 14.4ms) 표에서 뺐다.

### 2.9 2코어, 4GB 로 묶은 노드 하나 (D-51)

t3.medium(2 vCPU, 4GB)을 흉내 내 서버, PostgreSQL, Redis 를 같은 두 코어에 묶고(`--cpuset-cpus 0,1`), 메모리를 서버 1.6GB(힙 1GB), PostgreSQL 1.5GB, Redis 256MB 로 묶었다. 1.4 의 수용량 조건(문서 500 x 4명, 초당 1번, 60초)이다. 노트북 안의 컨테이너라 실제 서버의 디스크와 네트워크는 아니다.

| | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| 수렴 | 494/500 | 500/500 |
| 닫힌 연결 | 4009 로 24 개(커밋 실패로 세션을 버림 6번) | 없음 |
| ack p50, p95, p99, 최대 | 2.3ms, 489ms, 1,143ms, 3,175ms | 1.4ms, 27ms, 75ms, 233ms |
| 서버 ack 처리 평균 | 72.3ms | 3.7ms |
| 힙(살아 있는 연결 2,000) | 532MB | 513MB |
| CPU 최대(두 코어 = 200%) | 서버 131%, PostgreSQL 62% | 서버 125%, PostgreSQL 54% |

고친 것: 검색 본문(D-47)과 댓글 위치(D-50)를 쓰는 백그라운드 작업이 활성 문서마다 5초에 한 번, 동시 실행 수 제한 없이(가상 스레드) DB 에 썼다. 문서 500 개에서 이것들이 커밋과 같은 연결 풀(10개)을 다투다 커밋이 3초 안에 연결을 얻지 못해 세션을 버렸다(`CannotGetJdbcConnectionException`). 백그라운드 쓰기를 동시에 2개로 묶고, 본문이나 댓글 스레드 목록이 바뀌지 않았으면 쓰지 않게 했다. 처음에는 CPU 를 컨테이너마다 나눠(서버 1.4, PostgreSQL 0.4) 쟀는데, PostgreSQL 이 자기 몫에 묶여 결과가 훨씬 나빴다(커밋 실패 376번). 실제 서버는 두 코어를 나눠 쓰므로 같은 코어에 묶는 방식으로 바꿨다.

## 3. 고친 것의 전후

### 3.1 PERF-1 원격 편집 반영 (#41, D-26)

- 원인: 문서의 `children` 이 부를 때마다 블록 전체를 훑었고(`frontend/src/collab/ot/document.ts`), 화면을 만드는 `flatten` 이 블록마다 불러 블록 수의 제곱이었다. 편집기에 반영할 때 바뀌지 않은 블록까지 글자 차이를 계산했다
- 고친 것: 부모별 자식 색인을 한 번 만들어 쓴다. 같은 노드는 글자 차이 계산을 건너뛴다
- 목표: 5,000 블록에서 원격 편집 하나 반영이 한 프레임(16ms) 안

| 블록 | 전 toPm / renderView | 후 toPm / renderView |
| --- | --- | --- |
| 500 | 3.5 / 4.1 ms | 0.2 / 0.4 ms |
| 2,000 | 50.1 / 55.2 ms | 0.9 / 1.3 ms |
| 5,000 | 299.2 / 301.2 ms | 1.7 / 3.1 ms |

색인만 넣었을 때 5,000 블록 renderView 는 15.2ms 였다. 시간은 기기마다 달라 시험으로 단언하지 않는다. 색인이 예전 계산과 같은지만 시험으로 고정한다.

### 3.2 PERF-2 커밋 경로의 DB 왕복 (#78, D-38)

- 원인: 커밋 하나가 묶음 N 개에 DB 를 2N+1 번 왕복했다. 묶음마다 중복 확인 SELECT 하나와 INSERT 하나, 그리고 COMMIT. DB 지연 실험에서 찾았고 `log_statement=all` 로 확인했다
- 고친 것: 중복 확인은 연결의 첫 묶음에서만(그 뒤는 순번이 늘기만 하는 규칙으로), INSERT 문 하나로 여러 행. 묶음이 1,000 개 이하면 크기와 상관없이 왕복 한 번이다. 넘으면(매개변수 한도 65,535 때문에) 1,000 행씩 나눠 한 트랜잭션 안에서 넣는다. 측정에서 커밋 묶음 크기는 최대 51 이었다

| 측정 | 전 | 후 |
| --- | --- | --- |
| DB 응답 +200ms, 4명 x 15번 | 30.4초(초당 2.0) | 7.0초(초당 8.6, 4.4배) |
| 로컬, 한 문서 50명 ack p50 / p95 / p99 | 3.3 / 9.3 / 13.0 ms | 1.9 / 5.9 / 9.1 ms |
| 로컬, 한 문서 100명 ack p50 / p95 / p99 | 11.6 / 75.6 / 125.8 ms | 3.5 / 17.1 / 47.2 ms |
| 로컬, 한 문서 100명 서버 ack 평균 | 16.0 ms | 3.53 ms |

진단 때 PERF-2 로 적었던 "묶음마다 블록 맵 전체 복사, merge 마다 블록 전체 훑기"(`Document.java`)는 따로 재거나 고치지 않았다. 위 측정에서 지연의 주된 원인은 DB 왕복이었다.

### 3.3 WebSocket 글 버퍼 (#73, D-36)

- 원인: Tomcat 은 WebSocket 글 메시지 버퍼를 연결마다 미리 잡는다. 크기는 char(2 바이트) 수이고, 한도(64KB)의 4배로 두어 연결당 약 512KB 였다
- 고친 것: 버퍼를 한도와 같게(65,536 글자, `CollabConfig.java:191`). UTF-8 에서 글자는 1 바이트 이상이라 한도 안의 메시지는 언제나 들어간다

| | 전 | 후 |
| --- | --- | --- |
| 연결 2,000 / 문서 500, 힙 1GB | 약 930 연결에서 OOM | 2,000 연결, 500/500 수렴, nack 0 |
| 연결당 char 버퍼 | 약 600KB | 약 131KB |
| ack p50 / p95 / p99 | - | 1.7 / 14.3 / 52.7 ms |
| 정점의 살아 있는 힙(GC 뒤) | - | 437MB |

### 3.4 클라이언트 전송 간격 (#69, D-34)

- 원인: 답이 빠르면 키마다 묶음 하나가 나갔다. 초당 50타에서 1초 창에 31개를 보내 서버가 4008(초당 30 초과)로 끊었고, 4008 은 치명이라 다시 붙지 않았다. CI 의 e2e 가 자주 실패한 원인이었다
- 고친 것: 묶음은 50ms 에 많아야 하나(초당 20개). 사이 입력은 다음 묶음 하나로 모인다. 서버 한도는 그대로
- 확인: e2e 에서 150자를 초당 50타로 쳐도 닫힘이 없고 1초 창의 묶음이 21개 이하. 간격을 0 으로 하는 변이에서 실패한다
- 부수 효과: 위 부하 측정의 묶음 수는 이 간격을 따른다. 측정한 ack 지연에는 이 간격의 대기가 들어가지 않는다(보낸 때부터 잰다)

## 6. 주의 사항

- 서버와 loadgen 이 같은 기기를 나눠 썼다. loadgen 의 CPU 사용이 서버 지연에 섞였고, 네트워크 지연은 거의 없다
- 노트북의 Docker Desktop 위 PostgreSQL 이다. 디스크와 fsync 특성이 서버와 다르다
- 측정은 대부분 한 번씩 돌린 값이다. 반복해 분산을 재지 않았다
- 가상 편집자는 블록 이동과 서식을 만들지 않는다. 13.3 의 "블록 이동 비율" 은 넣지 않았다
- 13.3 의 시나리오 가운데 "문서 열기(블록 100, 1,000, 5,000 x 스냅샷 간격 50, 200, 1,000)" 와 "커밋 방식 비교" 는 그 표대로 돌리지 않았다. 문서 열기는 2,000 블록 하나, 커밋 방식은 PERF-2 전후 비교로 대신했다
- 화면 측정(PERF-1)은 Node 에서 어댑터 함수만 잰 값이다. 브라우저의 그리기 시간은 들어가지 않는다

```
# 저장소와 서버
docker compose up -d

./gradlew :loadgen:run --args="scenario=one-doc editors=50 seconds=60 rate=5"

./gradlew :loadgen:run --args="scenario=many-docs docs=500 editors=4 rate=1 seconds=60"

# DB 지연, 느린 클라이언트 (Testcontainers, Toxiproxy)
./gradlew :app:test --tests '*DbLatencyTest' --tests '*SlowClientTest'

# 스냅샷 간격 (2.7)
./gradlew :app:test --tests '*SnapshotIntervalBench' -Dcopage.bench=true -i

# 노드 둘 (2.8). 관리 포트가 컨테이너 안에만 있어 지표는 비운다
docker compose -p copage-cluster -f deploy/cluster/compose.yaml up -d --build postgres redis node1 node2 proxy
./gradlew :loadgen:installDist
loadgen/build/install/loadgen/bin/loadgen base=http://localhost:8088 management=http://localhost:8088 scenario=many-docs docs=100 editors=3 seconds=30 rate=2

# 2코어, 4GB (2.9). 위 클러스터의 PostgreSQL, Redis 를 두 코어에 묶고 서버 하나를 같은 코어로 띄운다
docker update --cpus 2 --cpuset-cpus 0,1 --memory 1500m --memory-swap 1500m copage-cluster-postgres-1
docker update --cpus 2 --cpuset-cpus 0,1 --memory 256m --memory-swap 256m copage-cluster-redis-1
docker run -d --name copage-4g --network copage-cluster_cluster --cpuset-cpus 0,1 --memory 1600m --memory-swap 1600m \
  -p 18095:8080 -p 18096:8081 -e SPRING_DATASOURCE_URL=jdbc:postgresql://172.30.0.10:5432/copage \
  -e SPRING_DATA_REDIS_HOST=172.30.0.11 -e SPRING_PROFILES_ACTIVE=dev -e COPAGE_MANAGEMENT_ADDRESS=0.0.0.0 \
  -e JAVA_TOOL_OPTIONS=-Xmx1g -e COPAGE_JWT_SECRET=<32바이트 이상> copage-cluster-node1
loadgen/build/install/loadgen/bin/loadgen base=http://localhost:18095 management=http://localhost:18096 scenario=many-docs docs=500 editors=4 rate=1 seconds=60

# 화면 반영 (PERF-1)
cd frontend && npm run perf
```

- 500 x 4 실행의 `seconds` 는 기록하지 않았다. 위 명령의 60 은 예다
- 노드 강제 종료 실험의 명령은 [CHAOS.md](../CHAOS.md) 에 있다
- loadgen 은 끝에 보낸 묶음, nack, 닫힘, ack 와 remote 지연 분포, 서버 지표(ack 처리 평균, 세션, 연결, 힙, CPU), 수렴 여부를 출력한다. 커밋 묶음 크기는 관리 포트의 `collab_commit_batch_size` 로 본다
