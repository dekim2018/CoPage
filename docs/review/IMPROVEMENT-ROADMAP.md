# 남은 개선 일

진단 개선(1~4단계)을 마친 뒤 남은 일을 우선순위대로 적는다. 항목마다 왜 필요한지, 대략의 크기, 앞서 끝나야 할 일을 적는다.

- 크기는 지금까지의 PR 크기에 견준 어림이다. **작음**: PR 하나, **중간**: PR 둘~셋, **큼**: PR 넷 이상. 재서 정한 값이 아니다
- 진단에서 온 항목은 진단 ID(DC, SEC, PERF)를, 결정에서 미룬 항목은 D-xx 를 함께 적는다
- 제품 기능의 ID(W, S, R, E, V, C, F)는 [01-PLAN.md](../01-PLAN.md) 2장, 단계는 [12-ROADMAP.md](../12-ROADMAP.md) 14.1 이다

## 2. 진단에서 남은 일

### 1. 다중 노드 소유권 (DC-1, 로드맵 4단계)

- 왜: 지금은 노드 1대라 한 문서를 한 세션만 든다. 노드가 늘면 두 노드가 같은 문서 세션을 들 수 있다. 쓰기는 `doc_ops (doc_id, rev)` 기본 키가 막지만(D-04), 쓰기가 없으면 오래된 노드가 낡은 welcome 과 remote 를 계속 준다. 1.4 의 "노드 장애 후 편집 재개 10초" 도 지금은 같은 노드를 다시 띄우는 경우만 쟀다
- 할 일(03-ARCHITECTURE 5.3, 5.4, D-04 의 방향)
  - Redis 리스 `doc:{docId}:owner`(`SET NX PX`, 주기 연장). 리스는 "누가 세션을 들지" 만 정한다. 정합성은 계속 DB 기본 키
  - 리스를 잃거나 연장하지 못하면 세션을 내리고 연결을 4009 로 닫는다. 오래된 노드가 낡은 상태를 주는 길을 막는다
  - 프록시 해시 라우팅(`/ws/docs/{docId}` 경로 해시)
  - 노드 추가와 계획된 종료의 양도(남은 묶음 커밋, 스냅샷, 4009, 리스 풀기)
  - 리스 충돌 지표(13.4 에서 빠진 하나)
  - 파생 쓰기(페이지 제목, D-21)가 오래된 노드에서 오지 않게 한다. 연산과 같은 트랜잭션(Outbox)에 넣거나 리비전으로 거른다
  - Redis 장애와의 관계를 정한다. 지금 편집 연결은 Redis 없이 계속된다(D-03). 리스가 생기면 Redis 장애 동안 리스를 연장하지 못한다. 그때 세션을 내릴지 유지할지가 새 결정이다
- 크기: 큼
- 앞선 일: 없음. 2, 3 이 이것에 기댄다

### 2. 다중 노드 전파

- 왜: 권한 변경 알림은 같은 프로세스의 세션에만 닿는다(D-17). 노드가 여럿이면 회수된 사람이 다른 노드에서 계속 편집한다. 사이드바도 남의 트리 변경을 받지 않는다(D-23)
- 할 일: Redis pub/sub `perm:changed`, `ws:{workspaceId}:tree`(03-ARCHITECTURE 5.5). 사이드바 SSE(W-5). pub/sub 은 메시지를 잃을 수 있으므로, 잃었을 때 다음 재접속에서 바로잡히는지(권한은 티켓 발급 때 다시 계산한다) 확인하고 적는다
- 크기: 중간
- 앞선 일: 1

### 3. 노드 2대 장애 실험

- 왜: 11-TEST-PLAN 13.2 의 실험 가운데 노드 일시 정지와 리스, 노드 추가가 남았다([CHAOS.md](../CHAOS.md) "남은 실험"). 12-ROADMAP 4단계의 완료 기준이 "노드 2대에서 장애 실험 7종 통과" 다
- 할 일: 소유 노드 일시 정지(리스 만료 뒤 다른 노드가 넘겨받고, 깨어난 노드의 쓰기는 기본 키로 실패), 노드 추가 중 양도, 다른 노드가 넘겨받는 경우의 재개 시간. loadgen 의 `reconnect=true` 를 쓴다
- 크기: 중간
- 앞선 일: 1, 2

### 4. 실제 4GB 서버에서 수용량 측정

- 왜: 1.4 의 노드 수용량(문서 500, 연결 2,000)은 노트북에서 힙 1GB 로만 맞췄다. 목표 조건은 4GB 서버이고, N-5 는 그 서버에 노드 2대, PostgreSQL, Redis, 프록시를 함께 올린다. 노트북 측정은 10코어와 넉넉한 메모리를 썼고 loadgen 이 같은 기기에 있었다([PERFORMANCE-REVIEW.md](PERFORMANCE-REVIEW.md) 6장)
- 할 일: 4GB 서버 한 대에 N-5 구성을 올리고, loadgen 을 다른 기기에서 돌린다. 한 문서 50명, 문서 500 x 4명, 문서 열기(스냅샷 뒤 연산 200개 조건 포함), 재접속 몰림. 13.3 의 시나리오 가운데 그 표대로 돌리지 않은 "문서 열기(블록 수 x 스냅샷 간격)" 도 함께 돈다
- 크기: 중간
- 앞선 일: 3, 배포 준비(16)

### 5. 수렴 시뮬레이션 100만 회

- 왜: 1.4 의 수렴 정확성 조건은 "무작위 동시 편집 시뮬레이션 100만 회" 다. CI 는 시뮬레이션 15,000회와 TP1 쌍 1,000,000개를 돈다. 시뮬레이션 100만 회는 돌리지 않았다
- 할 일: `./gradlew :ot-core:test --tests '*ConvergenceSimulationTest' -Dcopage.ot.scale=667` 처럼 배수를 키워 한 번 돌리고 결과(시간, 편집, 확정, 거부, 재접속 수)를 1.4 와 PERFORMANCE-REVIEW 에 적는다. CI 에 넣지 않고 따로 돌린다. 걸리는 시간은 재지 않았다
- 크기: 작음
- 앞선 일: 없음

### 6. welcome 에 서버 메시지 한도 싣기 (#74 리뷰)

- 왜: 서버 한도(`copage.collab.max-message-bytes`)는 설정이지만 클라이언트의 묶음 크기 한도는 60,000 바이트로 고정이다(`sendBudget.ts`). 운영자가 서버 한도를 60,000 보다 작게 줄이면 정상 클라이언트가 4008 로 끊긴다. 지금은 "줄이지 않는다" 는 주석으로만 막는다
- 할 일: welcome 에 한도를 더하고(필드 추가라 예전 클라이언트는 무시한다), 클라이언트가 그 값에서 여유를 뺀 만큼으로 나눈다. Java `ClientSession` 은 나누지 않으므로 loadgen 은 그대로다(D-37)
- 크기: 작음
- 앞선 일: 없음

### 7. 속성 값의 서버 길이 한도 (#74 리뷰, D-29)

- 왜: 속성 값 하나가 60KB 를 넘으면 클라이언트가 나눌 수 없어 그대로 보내고 4008 로 끊긴다. 지금 편집기는 짧은 값(링크, 체크, 제목 단계)만 만들어 생기지 않는다. 서버는 language 만 32자로 막고 다른 값의 길이는 메시지 한도에 맡긴다
- 할 일: `ChangePolicy` 에 값 길이 한도(예: 링크 주소)를 두어 nack(input)으로 거부한다. 4008(치명)이 아니라 nack 가 되어 편집기가 멈추지 않는다
- 크기: 작음
- 앞선 일: 없음

### 8. WebSocket 부분 메시지 조립 (D-36)

- 왜: 컨테이너가 연결마다 글 버퍼를 미리 잡아 연결당 약 131KB, 연결 2,000개에 263MB 다. 힙 1GB 의 4분의 1 이다. 연결 수 목표를 늘리면 다시 한계에 닿는다
- 할 일: `supportsPartialMessages` 로 부분 메시지를 받아 직접 모은다. 크기 확인과 조립을 직접 짜야 한다. 한도를 넘는 순간 4008 로 끊고 모은 것을 버린다
- 크기: 중간
- 앞선 일: 연결 수 목표가 2,000 을 넘을 때 한다. 4 의 측정이 판단 근거다

## 3. 제품 로드맵의 남은 단계

12-ROADMAP 의 단계 가운데 이번 작업이 앞당긴 것은 3단계의 핵심(워크스페이스, 페이지 트리, 권한 계산, 연산 단위 인가, 연결 중 회수)과 6단계의 일부(loadgen, 측정, 병목 개선)다. 남은 것은 아래와 같다.

### 9. 초대 메일(W-1)과 공유 링크(S-4) — 3단계의 나머지

- 왜: 지금 멤버 추가는 가입한 사용자를 이메일로 바로 넣는 임시 경로다(D-22). 가입 여부를 OWNER 에게 알려 주는 한계가 있다. 링크로 권한을 주는 기능(9.4 의 4번)이 없다
- 할 일: 초대 테이블과 수락 흐름, 메일 발송. 공유 링크(등급, 만료일, 그 페이지 하나에만 적용). 링크로 들어온 사용자의 권한 계산을 `PermissionRules` 에 더한다
- 크기: 중간~큼
- 앞선 일: 메일 발송 수단(외부 서비스 선택은 사용자가 정한다)

### 10. 페이지 이동(W-3)과 휴지통(W-4)

- 한 것(#80, D-39): 이동 API(고리 금지, 그 페이지의 FULL 과 새 부모의 EDIT, 권한 변경 알림), 휴지통으로 보내기와 꺼내기, 휴지통 목록(보내기 전에 볼 수 있던 페이지만), 사이드바의 휴지통 단추와 휴지통 화면
- 남은 것: 끌어 옮기는 화면(5단계 끌기와 함께), 깊이 제한(06-DATA-MODEL 은 10 을 적었다. 지금 검사하지 않는다), 30일 뒤 하위와 연산 로그까지 실제로 지우는 배치
- 크기: 작음~중간
- 앞선 일: 2(트리 전파). 노드 1대라면 2 없이도 할 수 있다

### 11. 오프라인 저장 (R-6, 진단 DC-4, 4단계)

- 왜: 연결이 끊긴 채 탭을 닫으면 보내지 못한 편집이 사라진다
- 할 일: IndexedDB 대기열(10-FRONTEND 12.4). 다시 열 때 같은 clientId 와 순번으로 다시 보낸다. 순번 규칙(D-38: 새 연결의 첫 묶음에서 확정 여부를 확인)과 맞는지 시험한다
- 크기: 중간
- 앞선 일: 없음

### 12. 버전 기록과 복원(V-1, V-2), 로그와 삭제 블록 정리(DC-8) — 5단계

- 왜: 과거 시점을 보거나 복원할 수 없다. 연산 로그와 삭제 표시 블록이 끝없이 쌓인다
- 할 일: 시점 목록, 시점 문서 열기(스냅샷과 로그 재생, `SnapshotReplayPropertyTest` 가 같은 성질을 지킨다), 복원을 연산으로 제출. 로그 90일 정리와 삭제 블록 30일 정리(06-DATA-MODEL 8.3, 8.4)는 복원 가능한 범위를 정하므로 버전 기록과 함께 설계한다
- 크기: 큼
- 앞선 일: 없음

### 13. 댓글(C-1~C-3), 멘션과 알림(C-4) — 5단계

- 왜: P1 요구사항이다. 댓글 위치는 서식 표시(mark)로 둔다(ADR 0006)
- 할 일: comment 모듈, 본문 연산에 댓글 표시, 해결 처리. 멘션 알림은 notification 모듈과 SSE. 이벤트는 PostgreSQL Outbox 로 낸다(Kafka 는 쓰지 않는다, ARCHITECTURE-REVIEW 3.1)
- 크기: 큼
- 앞선 일: 알림의 노드 간 전달은 2

### 14. 검색(F-1, F-2) — 5단계

- 왜: P1 요구사항이다. 두 글자 한글 검색은 pg_bigm 으로 한다(ADR 0007)
- 할 일: 문서 변경 이벤트(Outbox)로 검색용 텍스트 갱신, 볼 수 있는 페이지만 결과에. 권한 계산을 결과마다 하므로 이때 권한 캐시(D-11)가 필요한지 잰다
- 크기: 중간
- 앞선 일: Outbox(13 과 함께 만들면 한 번에 된다)

### 15. 되돌리기(E-8) — 5단계

- 왜: 내가 한 편집만 되돌리는 기능이 없다. 역연산은 Java 와 TS 모두 있다(`InverterPropertyTest`, `frontend/src/collab/ot/inverter.ts`)
- 할 일: 내 편집의 역연산을 쌓고, 남의 편집이 들어오면 변환해 옮기는 되돌리기 목록. 화면 단축키 연결
- 크기: 중간
- 앞선 일: 없음

### 16. 배포 준비 — 7단계

- 왜: 공개 주소에서 두 계정이 동시 편집하는 것이 7단계의 완료 기준이다
- 할 일: 운영 프로필과 비밀 주입(`COPAGE_JWT_SECRET` 등), Caddy 설정(TLS, X-Forwarded-*, 접근 로그의 `ticket` 가리기, IP 빈도 제한), 생존 검사를 `/actuator/health/liveness` 로, 관리 포트를 공개망에 내지 않기, README, 에러 모니터링 SDK 자리
- 실제 AWS 배포(계정, 비용, 도메인)는 소유자가 한다
- 크기: 중간
- 앞선 일: 4 와 함께 하면 같은 서버로 수용량을 잰다
