# 아키텍처 진단 개선 작업의 결정 기록

시니어 백엔드 아키텍처 진단(2026-11-23)을 처리하면서 내린 결정을 모은다. 결정마다 고른 안, 버린 안, 이유, 영향, 근거(PR, 측정)를 적는다.

- **사용자 확정**: 사용자가 직접 고른 결정
- **추천 채택**: 2026-11-24 사용자 지시("결정해야 하는 순간이 오면 추천대로 작업하고 문서로 남긴다")에 따라 추천안으로 정한 결정

결정을 뒤집을 때는 지우지 않고, 새 항목을 더하고 옛 항목에 "대체됨"을 적는다.

## 진행 방식

### D-01 작업 단위마다 브랜치, PR, 스스로 리뷰, 머지 (추천 채택, 2026-11-24)

- 결정: 문제 하나(또는 PR 하나로 볼 만한 묶음)마다 `feature/NN-이름` 브랜치를 develop 에서 만든다. PR 을 열고, PR 에 줄 단위 리뷰 댓글을 단 뒤 반영 커밋을 올리고 스레드를 해결 처리한다. `./gradlew build`, `npm run build`, `npm test`, 필요하면 Playwright e2e 가 통과하면 develop 에 머지하고 다음 작업으로 간다
- 버린 안: PR 을 쌓아 두고 사용자 머지를 기다린다. 다음 작업이 앞 PR 위에 쌓여 충돌과 리베이스가 늘어난다
- 이유: 사용자가 5단계까지 묻지 않고 진행하라고 했다. 그동안 PR 마다 같은 절차(리뷰 댓글, 반영, 해결 처리, 머지)를 사용자가 매번 지시했으므로 그 절차를 그대로 따른다

## 2단계 확정 결정 (사용자 확정, 2026-11-23)

### D-02 권한(SEC-1)은 설계 9.4 를 앞당겨 PR 넷으로 나눈다

워크스페이스와 페이지 → 권한 계산과 티켓 → 부여와 회수와 연결 중 회수 → 화면. 버린 안: `doc_access` 하나로 최소 공유. 3단계에서 워크스페이스 모델로 다시 만들어야 한다.

### D-03 Redis 장애 시 막힘(fail-closed)

Redis 가 필요한 요청은 503. 열린 편집 연결은 계속. 버린 안: 토큰 차단 확인만 건너뛰는 열림(fail-open). 로그아웃한 토큰과 탈취로 막은 토큰이 장애 동안 다시 통한다.

### D-04 펜싱 토큰은 도입하지 않는다

`doc_ops (doc_id, rev)` 기본 키와 노드마다 연속인 리비전이 낙관적 동시성 검사 역할을 한다. 다중 노드에서 Redis 리스는 "누가 세션을 들지"에만 쓰고 정합성은 DB 기본 키로 지킨다. ADR 로도 남긴다(5단계).

### D-05 순서 키(DC-5)는 정수부 가변 길이 키

기존 키와 섞여도 순서가 맞게 하고, Java, TS, 적합성 벡터를 함께 바꾸고, 서버에 키 최대 길이를 둔다. 버린 안: 재균형(동시 재균형이 순서를 섞어 서버가 단일 작성자여야 한다), 길이 한도만(성장이 남는다).

## 3단계 작업 중 내린 결정

### D-06 세션 기록 창은 별도 설정이고, 창 밖 baseRev 는 nack 대신 4011 로 닫는다 (PR #19)

- `copage.collab.history-window`(기본 5000)를 `rebase-max-gap` 과 나눈다. 둘은 다른 뜻이다(연결 중 변환 한도와 재접속 합치기 기준)
- nack 를 받으면 클라이언트가 묶음과 대기 편집을 버리므로, 창보다 뒤처진 연결은 4011 로 닫아 resume 으로 다시 맞추게 한다. 규약 형식은 바뀌지 않는다

### D-07 presence 한도 초과분은 끊지 않고 버린다 (PR #21)

연결마다 초당 30개. 정상 클라이언트는 50ms 마다 하나(초당 20개)라 걸리지 않는다. 몰아 보낸 마지막 커서가 버려지면 낡은 커서가 남을 수 있다는 한계는 주석에 적고 받아들인다.

### D-08 Refresh 토큰 회전은 기한을 붙인 스크립트 하나로 (PR #23)

시간 초과로 포기한 Redis 명령도 Redis 가 돌아오면 실행된다(일시 정지 실험으로 확인). 회전이 늦게 실행되면 세션을 잃으므로 (1) 주인과 사용자를 먼저 읽고 (2) 옛 토큰 표시와 새 토큰 저장을 한 스크립트로 하고 (3) 기한(명령 시간 한도의 절반)이 지난 실행은 아무것도 바꾸지 않는다. 버린 안: "후계 토큰이 안 쓰였으면 다시 회전" 은 유예 밖 탈취 판정을 약하게 한다.

### D-09 기존 문서는 첫 작성자의 "가져온 문서" 워크스페이스로 옮긴다 (PR #25)

V3 가 지우지 않고 옮긴다. 첫 작성자가 users 에 없는 문서(로그인 도입 전 개발 데이터)는 옮기지 않고 로그를 남긴다. 그 문서는 페이지가 없어 열 수 없다.

### D-10 없는 것과 볼 수 없는 것은 같은 404 (PR #25, #29)

속하지 않은 워크스페이스, 없는 페이지, 휴지통 페이지는 모두 404. 속해 있지만 등급이 없으면 403. 존재 여부를 흘리지 않는다.

### D-11 권한 캐시는 두지 않는다 (PR #29)

재귀 CTE 하나로 계산한다. 캐시 무효화 시점을 잘못 잡으면 회수한 권한이 남는다. 4단계 부하 측정에서 병목이면 그때 넣는다.

### D-12 목록의 hasChildren 은 권한을 보지 않고 센다 (PR #29)

볼 수 없는 하위 페이지만 있어도 true 다(존재가 드러나지만 제목과 ID 는 아니다). 화면(SEC-1-4)에서 펼침 단추를 쓰기 전에 다시 본다.

## SEC-1-3 권한 부여와 회수

### D-13 워크스페이스에 없는 사용자에게 페이지 권한을 주면 GUEST 로 넣는다 (추천 채택)

- 버린 안: 멤버에게만 줄 수 있게 한다. 9.4 의 GUEST("초대받은 페이지만 접근")가 생기는 길이 없어진다
- 영향: 권한을 주는 사람(그 페이지의 FULL)이 워크스페이스 멤버 목록을 바꾼다. GUEST 는 기본 권한이 없어 그 페이지(와 하위) 말고는 아무것도 보지 못한다

### D-14 restricted 를 켜는 사람이 OWNER 가 아니면 그 페이지에 자신의 FULL 을 남긴다 (추천 채택)

- 이유: FULL 을 조상에서 물려받은 사람이 경계를 켜면 경계 위의 부여가 끊겨 자기 자신이 잠긴다. 켠 사람이 그 페이지를 계속 관리할 수 있어야 한다
- 버린 안: 그대로 잠기게 둔다(되돌릴 사람이 OWNER 뿐), 잠기면 거부한다(경계를 켤 수 없는 경우가 생긴다)
- 알려진 한계(PR #31 리뷰): 제한을 다시 풀어도 이 FULL 은 남는다. 나중에 그 사람의 조상 FULL 을 회수해도 이 페이지와 하위의 FULL 은 남는다. 권한 목록에는 "이 페이지에 준 것"으로 보이므로 숨은 권한은 아니다. 자동 부여를 표시해 풀 때 지우는 방법(auto 플래그)은 사용자가 직접 같은 부여를 했는지 구분해야 해서 지금은 하지 않는다

### D-15 마지막 OWNER 는 내보내거나 내릴 수 없다 (추천 채택)

워크스페이스를 관리할 사람이 없어진다. 확인과 변경은 워크스페이스 단위 advisory lock 안에서 해, 두 OWNER 가 서로를 동시에 내리는 경우도 막는다.

### D-16 워크스페이스에서 내보내면 그 워크스페이스의 페이지 권한도 지운다 (추천 채택)

남겨 두면 다시 넣었을 때 옛 권한이 되살아난다. 내보낸 직후에는 역할이 없어 어차피 NotFound 다.

### D-17 권한 변경은 프로세스 안 포트로 알리고, 다중 노드 전달은 4단계에서 (추천 채택)

- `PermissionChangeListener` 포트로 "영향받는 페이지와 사용자"를 알린다. 커밋한 뒤에 부른다
- 워크스페이스 역할 변경과 내보내기는 "그 사용자의 모든 페이지"로 알린다. 워크스페이스의 페이지 ID 를 모두 싣지 않는다. 받는 쪽은 그 사용자의 열린 연결만 다시 계산하므로 사용자가 범위를 충분히 좁힌다
- 받는 쪽(collab)은 열린 세션 가운데 그 페이지의 연결만 다시 계산한다
- 노드가 여럿이면 다른 노드의 세션은 알림을 받지 못한다. 로드맵 4단계(다중 노드)에서 Redis pub/sub 으로 넓힌다. 그때까지 노드 1대 기준이다

### D-18 COMMENT 는 편집기에서 읽기 전용이다 (추천 채택)

9.4 표에서 COMMENT 는 댓글만 달 수 있고 본문은 못 고친다. 서버는 이미 COMMENT 의 본문 연산을 거부한다(9.5). 화면도 EDIT 미만이면 편집기를 읽기 전용으로 두고 도구 막대를 숨긴다. 그전에는 화면이 welcome 의 등급을 보지 않아, 읽기 권한으로도 편집기가 열리고 친 글자가 nack 로 사라졌다.

### D-19 등급을 다시 계산하는 일은 세션 실행 흐름 밖에서 (추천 채택)

세션 실행 흐름에서 대상 연결을 모으고, 저장소 읽기는 background 에서 하고, 적용은 다시 실행 흐름에서 한다. 실행 흐름을 DB 읽기로 막으면 그 문서의 모든 편집이 그만큼 늦어진다. 계산이 실패하면 아무것도 바꾸지 않는다. 다음 재접속 때 새 티켓이 바른 등급을 준다.

### D-20 권한이 내려간 연결의 보내던 편집은 nack 로 버려진다 (받아들임)

등급이 내려간 뒤 도착한 묶음은 새 등급으로 검사해 nack 한다. 클라이언트는 nack 를 받으면 그 묶음을 버린다(진단 DC-3). 권한이 회수된 사람의 편집이 남지 않는 것이 맞으므로 받아들인다. DC-3 을 고칠 때도 이 경우는 버리는 쪽으로 둔다.

### D-21 페이지 제목은 커밋 뒤 루트 블록에서 채우고, 리비전으로 순서를 지킨다 (추천 채택, #26)

- 문서 세션이 루트 블록 글이 바뀐 커밋 뒤에 `TitleSink` 포트로 알리고, workspace 모듈이 `pages.title` 에 쓴다. 알림은 세션 실행 흐름 밖에서 하므로 편집이 기다리지 않는다
- 알림이 순서 없이 도착할 수 있어 `pages.title_rev` 를 두고 더 큰 리비전으로만 바꾼다(V5)
- 세션을 올릴 때도 한 번 알린다. 제목 동기화 전에 만든 페이지는 처음 열릴 때 채워진다. 한 번도 열리지 않은 옛 페이지는 빈 제목으로 남는다(화면은 "제목 없음" 으로 보인다)
- 앞뒤 공백은 빼고 200 코드 단위에서 자른다(서로게이트 쌍은 가르지 않는다)
- 버린 안: 스냅샷 때만 갱신(싸지만 200 연산이나 세션 내릴 때까지 늦다), 모든 문서를 재생해 채우는 일괄 작업(옛 개발 데이터에 비해 비용이 크다)
- 모듈 관계: collab 이 workspace 의 공개 서비스(`WorkspaceService.updateTitle`)를 설정에서 잇는다. 권한 검사가 없는 서버 내부 경로다

### D-22 화면 경로와 임시 멤버 화면 (추천 채택, SEC-1-4)

- 편집기는 `/w/:workspaceId/p/:pageId`. 예전 주소와 공유받은 주소 `/p/:pageId` 는 `GET /api/pages/{id}` 로 워크스페이스를 찾아 옮긴다. 볼 수 없으면 그 자리에서 "열 수 없다" 를 보인다
- 멤버는 가입한 사용자를 이메일로 바로 넣는다. 초대 메일과 수락(W-1)은 메일 발송 인프라가 필요해 미룬다. 이 경로는 가입 여부를 OWNER 에게 알려 주는 한계가 있다(PR #25)

### D-23 사이드바는 다른 사람의 트리 변경을 바로 받지 않는다 (추천 채택, SEC-1-4)

W-5(P1, SSE)는 별도 작업으로 둔다. 화면을 다시 열거나 펼치면 새로 읽는다. 내가 만든 페이지와 내가 고친 제목(편집기의 제목 줄)은 바로 반영한다. 다른 사람이 고친 제목은 서버에 커밋 뒤 저장되고(D-21) 다음에 읽을 때 보인다

## P1

### D-24 순서 키: 맨 뒤와 맨 앞은 첫 글자 아래에서 세고, 서버에 모양과 길이 한도 (D-05 의 구현, #27)

- D-05 는 "정수부 가변 길이 키(fractional-indexing 방식)" 였다. 그 방식은 키 첫 글자가 정수부 길이를 뜻해서, 지금 키("V", "aV", "000001V")와 같은 규칙으로 읽을 수 없다. 두 모양이 섞인 형제 사이에서 키를 만들려면 옮기기(마이그레이션)나 두 규칙 혼용이 필요하다
- 그래서 같은 목표(맨 뒤, 맨 앞 추가에서 키가 로그로만 자람)를 키 모양을 바꾸지 않고 이룬다. 첫 글자가 같은 키들 안에서 정해진 길이(가운데 'V' 에서 멀수록 1, 2, 3, 최대 4)로 하나씩 세고, 다 쓰면 첫 글자를 옮긴다. 'z'(맨 앞은 '0')로 시작하는 키는 그 글자를 떼고 나머지에서 한다. 예전 키와 섞여도 문자열 순서 그대로라 옮기기가 필요 없다. 사이에 넣기는 예전 가운데 고르기를 그대로 쓴다
- 측정(2026-11-24): 맨 뒤에 1,000번 3글자(예전 167), 10,000번 4글자(예전 1,667), 1,000,000번 5글자. 맨 앞은 1,000번 3글자(예전 201). 예전 방식으로 길어진 'zzzzzV' 뒤에 1,000,000번 붙여도 10글자
- 서버는 블록 연산(insert, split, move)의 순서 키를 검사한다. 모양이 틀리면(빈 키, 0 으로 끝남, 쓸 수 없는 글자) 거부한다. 다른 클라이언트의 키 만들기가 실패하지 않게 하기 위해서다. 길이는 256 글자까지다. 같은 두 키 사이에 1,271~1,525번 거듭 끼워 넣어야 닿는다
- Java 와 TS 를 함께 바꾸고, 적합성 벡터에 맨 뒤와 맨 앞 추가를 길게 이어 가는 사례 3,600건을 더했다(예전 방식으로 길어진 키에서 시작하는 줄 포함)
- 알려진 한계(PR #37 리뷰): 256 글자 한도에 걸린 묶음은 nack 되고, 클라이언트는 nack 받은 묶음을 버린다(DC-3). 같은 두 블록 사이에 1,200번 넘게 거듭 끼워 넣어야 생긴다. 이웃 키를 다시 나누는 재균형(D-05 에서 버린 안) 없이는 더 짧은 키를 고를 수 없으므로 받아들인다. DC-3 을 고칠 때 이 거부 사유를 사용자에게 보인다

### D-25 지표는 관리 포트, 히스토그램, 정해진 레이블만 (추천 채택, OPS-1)

- Micrometer + Prometheus. 13.4 의 지표 가운데 리스 충돌(리스가 아직 없다)을 뺀 일곱 가지와 HTTP, JVM 기본 지표
- 관리 포트(기본 8081)에 기본으로 127.0.0.1 에서만 받는다. API 포트의 /actuator 는 막는다. 관리 포트로 들어온 요청만 여는 보안 체인을 따로 둔다(관리 포트가 따로 없으면 그 체인은 어디에도 맞지 않는다). 버린 안: API 포트에 토큰을 걸어 연다(토큰 관리가 늘고, 실수로 열릴 길이 생긴다)
- 분포는 히스토그램. 노드마다 계산한 백분위는 여러 노드를 합칠 수 없다. Micrometer 의 Prometheus 등록기는 히스토그램을 켜면 직접 계산한 백분위를 내지 않는다(실측)
- 레이블은 nack 의 분류(permission, input, empty, rejected) 하나다. 문서 ID 와 사용자 ID 는 넣지 않는다. 가짓수가 문서와 사용자 수만큼 늘어난다
- 생존 검사는 `/actuator/health/liveness` 다(PR #39 리뷰). 묶은 health 는 Redis 를 보므로 생존 검사에 쓰면 Redis 장애가 노드 재시작으로 번져 D-03 이 깨진다

### D-26 원격 편집 하나 반영은 5,000 블록에서 한 프레임(16ms) 안 (추천 채택, PERF-1)

- 완료 조건의 "정해 둔 시간" 을 한 화면 프레임(60fps 기준 16ms)으로 정한다. 그보다 길면 입력이 끊겨 보인다
- 원인 둘을 고쳤다. (1) 문서의 `children` 이 부를 때마다 블록 전체를 훑었다. 문서는 바뀌지 않으므로 부모별 자식 색인을 처음 한 번 만들어 쓴다. (2) 편집기에 반영할 때 바뀌지 않은 블록까지 글자 차이를 계산했다. 같은 노드는 건너뛴다
- 측정(`npm run perf`, Node 22, 로컬 개발 기기, 가운데 블록에 글자 하나):

  | 블록 | 전 (toPm / renderView) | 후 (toPm / renderView) |
  | --- | --- | --- |
  | 500 | 3.5 / 4.1 ms | 0.2 / 0.4 ms |
  | 2,000 | 50.1 / 55.2 ms | 0.9 / 1.3 ms |
  | 5,000 | 299.2 / 301.2 ms | 1.7 / 3.1 ms |

- 시간은 시험으로 단언하지 않는다(기기마다 다르다). 측정은 `npm run perf` 로 따로 돌린다. 색인이 예전 계산과 같은지는 시험으로 고정한다
- Java 의 `Document.children` 도 같은 방식이지만 디버그 출력에만 쓰여 그대로 둔다

### D-27 거부되거나 버려진 편집은 블록 단위로 살리고, 못 살린 글은 보관함에 (추천 채택, DC-3)

- 문제: 서버가 묶음을 거부하거나(nack), 다른 사람의 편집과 변환이 충돌하거나, 오래 떨어져 rebase:false 를 받으면 클라이언트가 그 묶음과 그 위에 쌓인 입력을 통째로 버렸다
- 살리는 기준: 블록 단위다. 한 블록의 글(text)과 속성(setProps) 편집은 다른 블록의 편집과 위치가 얽히지 않는다. 그래서 그 블록에 구조 편집(넣기, 나누기, 합치기, 옮기기, 지우기)이 섞이지 않았다면 그 블록의 편집만 떼어, 그 사이 확정된 다른 사람의 편집에 맞춰 변환하고 지금 문서에 다시 적용한다. 적용되면 새 묶음으로 다시 보낸다
- 살리지 않는 것:
  - 구조 편집. 거부된 바로 그 이유(충돌)일 가능성이 크다
  - 구조 편집이 닿은 블록의 편집, 지워진(보이지 않는) 블록의 편집, 변환이나 적용에 실패한 블록의 편집
- 다시 보내지 않는 경우:
  - 서버가 권한(permission), 입력(input), 빈 묶음(empty)으로 거부했으면 다시 보내도 거부된다. 권한 회수 뒤의 편집은 남지 않아야 한다(D-20)
  - 이미 한 번 살려 보낸 묶음이 다시 거부되면 되풀이하지 않는다
- 보관함: 살리지 못한 편집에서 사용자가 친 글을 편집기 위에 보이고 "글 복사" 를 둔다. rebase:false 의 대기 편집도 보관함으로 간다. 복사본 페이지로 남기는 일(7.5)은 미룬다
- 규약: nack 에 `code`(permission, input, empty, rejected)를 더했다. 더하기만 했으므로 예전 클라이언트도 그대로 동작한다. code 가 없는 nack 는 다시 보내지 않는다
- 상태 기계: TS 의 ClientSession 은 동작(Java 와 같은 규칙, 적합성 벡터 client.json)을 바꾸지 않고, 버린 편집과 그때 맞춰야 할 남의 편집을 따로 적어 둘 뿐이다. 살리기는 그 바깥(collabClient, salvage.ts)에서 한다
- 받아들이는 위험: 살려 다시 보낸 글이 그사이 바뀐 문맥에서 뜻이 달라질 수 있다(예: 남이 고쳐 쓴 문장 가운데 내 글자가 들어감). 같은 블록의 남의 편집에는 변환으로 위치를 맞추므로 글자가 엉뚱한 블록에 가지는 않는다

## P2

### D-28 인증 보강: Origin 직접 검사, iss/aud, 가입 409 유지, 티켓 주소 (추천 채택, SEC-4~7)

- SEC-4: 재발급과 로그아웃(쿠키로 인증하는 경로)은 컨트롤러가 Origin 을 직접 본다. Origin 이 없으면(브라우저가 아니거나 같은 출처) 받고, 같은 출처나 허용 목록이면 받는다. CORS 필터가 먼저 막지만, CORS 설정이 바뀌거나 필터가 빠져도 풀리지 않게 한다. 버린 안: CSRF 토큰. SameSite=Strict 와 Origin 검사로 충분하고 화면에 토큰 처리가 는다
- 프록시 뒤(PR #45 리뷰): 운영은 Caddy 가 TLS 를 끝내고 http 로 넘긴다. 같은 출처 판정이 https 를 보도록 `server.forward-headers-strategy: native` 를 켠다. Tomcat 은 내부 주소(127/8, 10/8, 192.168/16 등)에서 온 요청의 X-Forwarded-* 만 믿으므로, 밖에서 꾸민 헤더는 통하지 않는다. 프록시는 같은 기기나 내부망에 둔다
- SEC-5: Access 토큰에 iss(`copage.auth.issuer`, 기본 copage)와 aud(`copage.auth.audience`, 기본 copage-api)를 넣고 검증한다. 같은 비밀키를 다른 서비스와 나눠 쓰게 되어도 섞이지 않는다. 배포하면 그 전에 발급한 Access 토큰(최대 15분)은 401 이 되고, 화면은 Refresh 쿠키로 바로 다시 받는다
- SEC-6: 가입의 409(이미 가입한 이메일)는 유지한다. 가입 화면이 "이미 가입했다" 를 알려 주는 편이 사용자에게 낫고, 로그인은 이미 존재 여부를 숨긴다. 이메일 존재 확인을 대량으로 하는 공격은 가입 빈도 제한으로 막을 일이다. 공개 배포(로드맵 7단계) 때 프록시 단의 IP 빈도 제한과 함께 다룬다
- SEC-7: WebSocket 티켓은 주소(`?ticket=`)에 실린다. 30초 1회용이라 남아도 쓸모가 없고, 지금은 접근 로그를 켜지 않아 남는 곳이 없다. 프록시나 Tomcat 접근 로그를 켤 때 `ticket` 값을 가린다(배포 문서에 적는다). 버린 안: 첫 메시지로 티켓 보내기. 핸드셰이크에서 인증하는 지금 구조(9.3)를 바꿔야 한다

### D-29 블록 속성은 키마다 값을 검사하고 구분선은 글을 담지 않는다 (추천 채택, DC-6)

- 허용 키는 type, level(1~3 정수), checked(참거짓), language(32자 이하, 글자와 숫자와 + # . _ -). 다른 키는 거부한다. null 은 지우기라 받는다
- 블록 종류마다 허용 키를 나누지 않는다. 종류를 바꾼 뒤 예전 속성(문단이 된 제목의 level)이 남은 문서가 이미 있어, 그렇게 나누면 그 문서의 다음 편집이 거부된다. 화면은 모르는 속성을 무시한다
- 구분선은 결과 문서에서 글이 비어 있어야 한다(지운 구분선은 보지 않는다). 블록 종류는 결과 문서에서만 알 수 있어 문서 크기 검사와 같은 자리에서 본다

### D-30 확인되지 않은 내 편집이 있으면 커서를 미룬다 (추천 채택, e2e 에서 찾은 경쟁 조건)

- 증상: presence e2e 가 8번에 1번 실패했다. 상대 화면의 내 커서가 한 칸 뒤에 보였다. 내가 다음에 커서를 옮길 때까지 남는다
- 원인: 커서는 내 화면 문서 기준인데, 그 화면에는 아직 확정되지 않은 내 편집이 있다. 그 편집보다 커서가 먼저 남에게 닿으면, 남은 커서를 그 자리에 두었다가 내 편집을 받으며 한 번 더 옮긴다
- 결정: 확인되지 않은 편집이 있으면 커서를 미뤘다가, 모두 확인된 뒤 마지막 커서 하나만 보낸다. ack 는 서버가 내 편집을 남에게 보낸 다음에 오므로 순서가 지켜진다. 보내는 쪽 화면과 규약 형식은 그대로다
- 버린 안: presence 에 기준 리비전을 붙이고 받는 쪽이 변환한다(규약이 커지고, 확정되지 않은 내 편집은 받는 쪽이 알 수 없어 변환할 수도 없다)
- 비용: 연속해서 치는 동안 커서가 ack 한 번만큼(로컬 수 ms) 늦게 보인다
- 확인: 고친 뒤 presence e2e 2개를 15번씩(30번) 돌려 모두 통과했다

### D-31 무작위 생성기에 이모지와 긴 글, 스냅샷과 재생의 일치를 무작위로 (추천 채택, DC-7)

- 생성기(RandomOps)의 낱자에 이모지(서로게이트 쌍)와 국기(코드 포인트 둘)를 넣고, 스무 번에 한 번은 수백 낱자 긴 글을 넣는다. 위치는 편집기처럼 서로게이트 쌍의 가운데를 자르지 않게 맞춘다. 가운데를 자르는 연산은 편집기가 만들지 않으므로, 그런 경우까지 섞으면 실제로 없는 실패만 늘어난다
- 생성기를 Gradle test fixtures 로 옮겨 app 의 시험도 쓴다
- 스냅샷과 그 뒤 로그로 연 문서가 처음부터 다시 적용한 문서와 같은지, 무작위 리비전에 스냅샷을 남기며 실제 PostgreSQL 로 확인한다
- 생성기가 바뀌어 적합성 벡터도 다시 만들어진다. 새 벡터에는 이모지 수만~수백만 글자와 긴 글 수백~수만 개가 들어 있고 TS 가 모두 같다

### D-32 모듈 경계는 ArchUnit 으로, CI 에 비밀키와 의존성 검사 (추천 채택, ARCH-1, OPS-2)

- 모듈 경계 검사는 ArchUnit 시험(`ModuleBoundaryTest`)으로 한다. 규칙: 모듈 사이 순환 없음, 다른 모듈은 app 과 domain 으로만 쓴다(in, out, config 는 그 모듈 안의 것), domain 과 app 은 in, out, config 를 모른다, domain 은 스프링을 모른다
- 버린 안: Spring Modulith(02-TECH-STACK 에 적었던 것). Modulith 는 모듈의 하위 패키지를 모두 내부로 보아, 지금 구조(app 의 포트와 서비스를 다른 모듈이 씀)에서는 패키지마다 NamedInterface 를 달아야 한다. 같은 규칙을 ArchUnit 은 그대로 적을 수 있고 Spring Boot 판과도 엮이지 않는다
- 규칙이 실제로 잡는지: workspace.app 에서 collab.out 을 쓰는 임시 클래스를 넣으면 넷 중 셋이 실패한다
- CI: 커밋 이력 전체의 비밀키 검사(gitleaks, 판 고정), 화면 의존성의 high 이상 취약점(npm audit), 의존성 갱신 PR(Dependabot: gradle, npm, actions). 지금 결과: 비밀키 없음(커밋 72개), 취약점 0
- 하지 않은 것: 형식 검사와 정적 분석. 형식 도구를 들이면 코드 전체가 바뀐다. 사용자가 나중에 몰아서 할 리팩터링 때 함께 정한다

## 4단계 장애와 부하 시험

### D-33 DB 소켓 시간 한도와, 묶음 처리 중 저장소 실패도 세션 버리기 (추천 채택, PostgreSQL 중단 실험)

- 실험이 두 결함을 드러냈다. (1) 답하지 않는 DB 에 보낸 JDBC 질의는 끝없이 기다린다. (2) 커밋 전 중복 확인(committedRev)이 실패하면 예외가 실행기로 새어 묶음이 말없이 사라진다
- 소켓 시간 한도 10초(`COPAGE_DB_SOCKET_TIMEOUT_SECONDS`). 문서 세션의 질의는 짧아 10초는 넉넉하다. 버린 안: 문장 시간 한도(statement_timeout). DB 가 멈추면 서버 쪽 한도는 효과가 없다
- 묶음 처리 중 저장소 실패는 커밋 실패와 같이 세션을 버린다(4009). 메모리의 문서가 이미 이 차례의 앞 묶음을 적용했을 수 있어 그대로 이어 가면 저장소와 어긋난다. 처리하지 못한 묶음은 클라이언트가 같은 순번으로 다시 보낸다
- 마이그레이션(Flyway)은 앱의 연결 풀과 따로 연결한다(PR #68 리뷰). 소켓 시간 한도가 데이터를 옮기는 긴 마이그레이션을 끊어 서버가 뜨지 않는 일을 막는다
- 실험 결과와 남은 실험은 docs/CHAOS.md
### D-34 클라이언트는 묶음을 50ms 에 하나만 보낸다 (추천 채택, CI 간헐 실패 #54 의 원인)

- 증상: CI 의 첫 e2e(블록 10종)가 자주 실패했다. 화면은 "연결할 수 없다"
- 재현: 초당 50타(키를 누르고 있는 정도)로 치면 클라이언트가 초당 31개 묶음을 보내고, 서버가 4008("change 를 초당 30 개보다 많이 보냈다")로 끊었다. 4008 은 치명이라 다시 붙지 않는다. 답(ack)이 빠를수록 키마다 묶음 하나가 나가 더 잘 생긴다. CI 기기가 그런 경우였다
- 결정: 클라이언트가 묶음을 50ms 에 많아야 하나(초당 20개) 보낸다. 사이의 입력은 buffer 에 모여 다음 묶음 하나가 된다. 서버 한도(30)는 그대로 둔다. 비정상 클라이언트를 막는 한도이고, 정상 클라이언트가 그 아래에 머무르면 된다
- 버린 안: 서버 한도를 올린다(정상 클라이언트의 버릇을 그대로 두면 다른 기기 속도에서 다시 닿는다). 4008 을 치명이 아니게 한다(규약 위반을 되풀이하게 된다)
- 진단을 위해 서버가 4008 로 닫을 때 사유를 WARNING 으로 남긴다. 이번에는 로그가 없어 재현으로만 원인을 찾았다

### D-35 의존성 갱신 PR 처리 규칙 (추천 채택, Dependabot 이 연 PR 열두 개)

- CI 가 모두 통과하면 머지한다. 실패하면 원인을 본다. 이번의 e2e 실패 대부분은 #54(D-34)였고, 고친 뒤 다시 돌려 확인한다
- 받지 않는 것(설정의 ignore 로 다시 오지 않게 한다)
  - TypeScript 7: vue-tsc 가 TS 의 JS API 를 쓰는데 네이티브 구현(7.0)에는 없다. CI 의 타입 검사가 실제로 실패했다(#61)
  - @types/node 주 판 올림: 실행 환경(Node 22)과 타입의 주 판을 맞춘다(#64)
  - Jackson 단독 올림: Spring Boot 가 관리하는 판을 따른다. ot-core 의 시험 의존성(Jackson)은 Boot 를 올릴 때 같은 판으로 맞춘다(#65)
- 큰 판 올림(Spring Boot 4.1 → 4.2, JUnit 5 → 6, GitHub Actions 들)도 CI(빌드, 적합성, e2e)가 통과하면 받는다. 시험이 이 프로젝트의 동작을 지키는 그물이기 때문이다

### D-36 WebSocket 컨테이너의 글 버퍼를 메시지 한도와 같게 (추천 채택, 부하 시험에서 찾은 메모리 넘침)

- 증상: 문서 500개 x 편집자 4명(연결 2,000개, 1.4 의 노드 수용량 목표)을 붙이던 중 연결 약 930개에서 힙 1GB 가 넘쳤다(OutOfMemoryError)
- 원인: 컨테이너(Tomcat)는 글 메시지 버퍼를 연결마다 미리 잡는다. 크기는 글자(char, 2 바이트) 수다. 한도(64KB)의 4배로 두어 연결당 약 512KB 였다. 연결 400개에서 char 배열이 241MB 였다(jmap)
- 결정: 버퍼를 한도와 같게(65,536 글자). UTF-8 에서 글자는 1 바이트 이상이라 한도 안의 메시지는 언제나 들어가고, 바이트만 한도를 넘는 메시지(한글 3만 자 등)는 여전히 처리기까지 와서 4008 로 끊긴다(기존 시험 그대로 통과). 글자 수까지 넘는 메시지는 컨테이너가 1009 로 끊으므로 클라이언트가 1009 도 치명으로 보고 다시 붙지 않는다(다시 붙으면 같은 메시지를 또 보낸다)
- 결과: 연결 2,000개, 문서 500개가 힙 1GB 에서 돈다. 정점의 살아 있는 힙 437MB 중 char 버퍼 263MB(연결당 약 131KB)
- 버린 안: 힙을 늘린다(목표가 힙 1GB). 한도를 줄인다(규약 변경). 부분 메시지를 받아 직접 모은다(supportsPartialMessages). 버퍼를 미리 잡지 않아 연결당 메모리가 가장 작지만 크기 확인과 조립을 직접 짜야 한다. 연결 수가 목표를 넘어설 때 다시 본다(IMPROVEMENT-ROADMAP)

### D-37 큰 편집은 클라이언트가 64KB 안의 묶음들로 나눠 보낸다 (추천 채택, 부하 시험 중 찾은 규약과 구현의 차이)

- 규약(05-PROTOCOL 7.7)은 "큰 붙여넣기는 클라이언트가 여러 묶음으로 나눠 보낸다"고 적었지만 클라이언트에 나누는 코드가 없었다. 한글 2만 2천 자쯤(64KB)을 넘게 붙여넣으면 서버가 4008 로 끊고, 4008 은 치명이라 편집기가 멈췄다. 붙여넣은 글은 서버에 가지 못했다
- 결정: `ClientSession.poll` 이 buffer 앞에서부터 JSON 60,000 바이트 안에 드는 만큼만 inflight 로 옮기고 나머지는 buffer 에 남긴다. ack 뒤 다음 poll 이 이어서 보낸다(50ms 간격, D-34). 연산 하나가 한도를 넘으면 차례로 적용해 같은 결과가 되는 작은 연산으로 나눈다
  - 텍스트 연산: 앞 조각들이 만든 결과 글자 수만큼 retain 을 앞에 두고 나머지 조각을 잇는다. 큰 삽입은 서로게이트 쌍을 가르지 않고 자른다
  - 긴 글을 가진 새 블록: 빈 블록 넣기 + 텍스트 연산(다시 나뉜다)
  - 블록이 많은 붙여넣기: 연산 경계에서 나눈다
- 살린 편집(D-27)이 여러 묶음으로 나뉘면 마지막 묶음까지 살린 것으로 적어, 거부되었을 때 다시 살리기를 되풀이하지 않는다
- 버린 안: 서버 한도를 올린다(한도는 메모리와 처리 시간의 상한이다. 붙여넣기 크기에는 끝이 없다). 붙여넣기를 막는다(사용자 기능을 줄인다). 화면 편집기 쪽(Tiptap 어댑터)에서 나눈다(편집 경로가 여럿이라 빠지는 곳이 생긴다. 보내는 자리 한 곳에서 나누는 것이 확실하다)
- Java `ClientSession`(시험과 loadgen 이 쓴다)은 나누지 않는다. 적합성 벡터는 한도 안의 편집만 쓰므로 두 구현의 결과는 같다. 나누기는 보내는 쪽의 전송 정책이지 변환 규칙이 아니다

### D-38 커밋 경로의 DB 왕복을 묶음 수와 상관없이 일정하게 (추천 채택, 진단 PERF-2, DB 지연 실험이 근거)

- 측정: DB 응답마다 200ms 를 더한 실험(`DbLatencyTest`)에서 60개 묶음이 30.4초(초당 2.0) 걸렸다. 문장 로그로 보니 커밋 하나가 묶음 N 개에 DB 를 2N+1 번 왕복했다. 묶음마다 중복 확인 SELECT 하나와 INSERT 하나, 그리고 COMMIT
- 결정 1, 중복 확인은 연결의 첫 묶음에서만: 다시 보내는 묶음(이미 확정되었을 수 있는 것)은 언제나 재접속한 연결의 첫 묶음이다. 첫 묶음에서 그 순번의 확정 여부와 이 클라이언트의 가장 큰 순번을 질의 하나로 읽고, 그 뒤로 한 연결의 순번은 늘기만 해야 한다. 어기면 4008(규약 강화, 05-PROTOCOL 7.5 의 5번)
  - 저장소 확인을 그냥 빼지 않은 이유: 유일 제약 `(doc_id, client_id, client_seq)` 에 걸리는 묶음이 하나라도 섞이면 묶음 커밋 전체가 실패하고 세션을 버린다. 클라이언트 하나가 문서의 모든 연결을 끊을 수 있게 된다. 순번이 늘기만 하는 규칙과 첫 묶음의 최대 순번 확인이 그 경우를 막는다
- 결정 2, INSERT 문 하나로 여러 행: 문장 하나는 자동 커밋에서도 원자적이라 BEGIN/COMMIT 이 필요 없다. 묶음 크기와 상관없이 왕복 한 번
- 결과: 같은 실험이 7.0초(초당 8.6, 4.4배). 로컬(DB 왕복이 짧다)에서도 한 문서 100명의 ack p99 125.8 → 47.2ms, 서버 ack 처리 평균 16.0 → 3.5ms
- 버린 안: JDBC batch(`reWriteBatchedInserts`). pgjdbc 설정에 기대고 BEGIN/COMMIT 왕복이 남는다. `unnest` 배열 INSERT. 문장은 고정되지만 jsonb 배열 변환이 번거롭다. 중복 확인을 묶음 전체에 한 번(IN 목록). 왕복은 한 번 남고, 한 연결 규칙이 없으면 위의 커밋 실패를 막지 못한다
- 호환: 정상 클라이언트(브라우저, Java ClientSession)는 이미 연결마다 순번을 늘리기만 한다. 같은 연결로 예전 순번을 다시 보내던 클라이언트는 이제 4008 로 끊긴다

### D-39 페이지 옮기기와 휴지통 (추천 채택)

- 권한: 옮기기는 그 페이지의 FULL 과 새 부모의 EDIT(최상위면 워크스페이스 역할의 기본 권한), 휴지통으로 보내기와 꺼내기는 FULL(09-API 의 표 그대로). 워크스페이스 멤버가 볼 수 없는 페이지는 GET 과 같이 403, 멤버가 아니거나 없는 페이지는 404
- 고리 막기: 워크스페이스 단위 advisory lock 안에서 새 부모에서 위로 거슬러 올라가 자기 자신이 나오는지 본다(06-DATA-MODEL 8.6). 두 사람이 동시에 서로의 아래로 옮겨도 하나만 된다(시험으로 확인, 잠금을 빼면 시험이 실패한다)
- 휴지통에는 보낸 페이지 자신만 있다(`archived_at`). 하위는 부모를 따라 보이지 않는다. 꺼내면 함께 돌아온다
- 꺼낼 때 부모가 아직 휴지통에 있으면 최상위 맨 뒤로 간다. 버린 안: 부모까지 함께 꺼낸다(사용자가 고르지 않은 것을 되살린다). 그대로 둔다(꺼냈는데 어디에도 보이지 않는다)
- 휴지통 목록은 휴지통에 가기 전에 볼 수 있던 페이지만 보인다(권한 계산에서 휴지통 여부만 빼고 같은 규칙, `accessIgnoringTrash`). 제한된 페이지의 제목이 새지 않게 하기 위해서다. 꺼내기 단추는 그때 FULL 이었던 사람에게만 보인다
- 옮기기, 보내기, 꺼내기 뒤에는 그 페이지와 하위의 권한 변경을 알린다(`PageGrants.treeChanged`). 옮기면 물려받는 권한이 바뀌고, 휴지통에 가면 열린 편집기가 1초 안에 닫힌다(4003, e2e 로 확인)
- 화면: 사이드바의 × 로 보낸다. 꺼낼 수 있어 묻지 않는다(브라우저 확인 창도 쓰지 않는다). 휴지통 화면에서 꺼낸다. 옮기기 화면(끌어 놓기)은 5단계의 끌기 작업과 함께 만든다. API 는 지금 있다
- 하지 않은 것: 30일 뒤 실제로 지우는 배치(06-DATA-MODEL). 연산 로그와 스냅샷까지 지워야 해 따로 다룬다(IMPROVEMENT-ROADMAP)
