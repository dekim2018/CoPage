# 데이터 정합성 진단 결과

아키텍처 진단의 정합성 항목(DC-1~DC-8)과, 지금 코드가 지키는 정합성 보장을 정리한다. 판정 방법은 [ARCHITECTURE-REVIEW.md](ARCHITECTURE-REVIEW.md) 2장, 설계는 [04-OT-DESIGN.md](../04-OT-DESIGN.md), [05-PROTOCOL.md](../05-PROTOCOL.md), [06-DATA-MODEL.md](../06-DATA-MODEL.md) 에 있다.

## 1. 지금 지키는 보장

| 보장 | 어떻게 지키나 | 시험 |
| --- | --- | --- |
| ack 받은 편집은 사라지지 않는다(N-1) | 커밋이 끝난 뒤에만 ack 와 다른 연결로의 전달을 한다(ADR 0005, `DocumentSession.drain`). 커밋이나 그 전의 저장소 읽기가 실패하면 세션을 버리고 4009(D-33) | `DocumentSessionTest`(커밋 실패 시 ack 없음, 변이 확인), `PostgresOutageTest`, `DbLatencyTest`(남에게 보인 묶음은 모두 이미 저장되어 있었다), 노드 `kill -9` 실험(ack 받은 묶음 유실 0, [CHAOS.md](../CHAOS.md)) |
| 한 문서의 리비전은 하나의 사슬이다 | `doc_ops` 의 `PRIMARY KEY (doc_id, rev)`. 두 작성자가 같은 리비전을 넣으면 한쪽이 실패한다. 펜싱 토큰 대신 이 기본 키를 최종 판정으로 쓴다(D-04) | `JdbcDocumentStoreTest` |
| 같은 묶음은 한 번만 적용된다(N-3) | `UNIQUE (doc_id, client_id, client_seq)`. 연결의 첫 묶음에서 그 순번의 확정 여부를 저장소에 묻고, 이미 확정되었으면 그 리비전으로 ack 한다. 그 뒤 한 연결의 순번은 늘기만 해야 하고, 어기면 그 연결만 4008(D-38) | `DocumentSessionTest`, `CollabWebSocketIntegrationTest`(무작위 끊김), `ConvergenceSimulationTest` |
| 묶음 커밋은 전부 아니면 하나도 아니다 | 여러 행을 INSERT 문 하나로 넣는다(`JdbcDocumentStore.java:106-133`). 문장 하나는 자동 커밋에서도 원자적이다. 1,000 행을 넘는 묶음(DB 가 멈췄다 돌아온 직후 등)은 1,000 행씩 나눠 한 트랜잭션 안에서 넣는다 | `JdbcDocumentStoreTest`(섞인 묶음은 하나도 쓰지 않는다) |
| 모든 클라이언트가 같은 문서로 수렴한다(R-1) | 서버가 순서를 정하는 OT(ADR 0001). Java 와 TS 두 구현을 적합성 벡터로 맞춘다(ADR 0009) | `TransformerPropertyTest`(TP1), `ConvergenceSimulationTest`, `InverterPropertyTest`, 적합성 벡터(TS 가 Java 와 모두 같다), loadgen 의 수렴 확인(모든 측정에서 수렴) |
| 스냅샷과 로그로 연 문서는 처음부터 재생한 문서와 같다 | 스냅샷은 `(doc_id, rev)` 기본 키에 `ON CONFLICT DO NOTHING`, 열 때 가장 새것을 읽고 그 뒤 로그를 적용한다 | `SnapshotReplayPropertyTest`(D-31, 실제 PostgreSQL, 무작위 리비전에 스냅샷), `RestartTest` |
| 세션 메모리가 끝없이 자라지 않는다 | 기록 창 5,000(`copage.collab.history-window`). 창 밖의 기록과 순번 맵은 버린다. 창보다 오래된 baseRev 는 4011 로 닫아 다시 맞춘다(D-06) | `SyncScenarioTest`, `DocumentSessionTest` |
| 순서 키가 맨 뒤와 맨 앞 추가에서 로그로만 자란다 | D-24 의 세기 방식. 서버가 모양과 길이 256 을 검사한다 | `FractionalIndexTest`, 적합성 벡터 3,600건 추가, `ChangePolicyTest` |
| 거부된 편집의 사용자 글이 말없이 사라지지 않는다 | 블록 단위로 살려 다시 보내고, 못 살린 글은 보관함에 보인다(D-27) | `salvage.test.ts`, e2e |
| 64KB 를 넘는 편집도 서버에 간다 | 클라이언트가 60,000 바이트 안의 묶음들로 나눈다(D-37) | `sendBudget.test.ts`, e2e(한글 5만 자 붙여넣기) |

## 2. 진단 항목별 결과

### DC-1 다중 노드 소유권 (MEDIUM, 열려 있음)

- 지금: 노드 1대라 문제가 생기지 않는다. 코드에 리스, 소유자, 세대 번호가 없다
- 쓰기 정합성: 다중 노드가 되어도 DB 기본 키가 지킨다. 두 노드가 같은 문서 세션을 들면 한쪽의 커밋이 실패하고, 그 노드는 세션을 버리고 4009 로 닫는다. 실패한 쪽의 클라이언트는 다시 붙어 ack 받지 못한 묶음을 다시 보낸다
- 남는 위험
  1. **읽기**: 쓰기가 없으면 오래된 노드가 낡은 상태로 welcome 과 remote 를 계속 줄 수 있다. 알아챌 방법이 없다
  2. **파생 쓰기**: 페이지 제목은 연산 INSERT 와 다른 트랜잭션에서 쓴다(D-21). `title_rev` 로 더 큰 리비전만 쓰지만, 오래된 노드가 리비전 사슬을 다르게 가진 경우는 따지지 않았다
  3. **권한 전파**: 권한 변경 알림이 다른 노드의 세션에 닿지 않는다(D-17)
- 계획(D-04, 2단계 계획)
  - Redis 리스(`SET NX PX`)는 "누가 세션을 들지" 만 정한다. 정합성은 계속 DB 기본 키가 지킨다. 리스 세대 번호를 DB 에 따로 둘 근거는 지금 없다
  - 리스를 잃은 노드는 세션을 내리고 연결을 4009 로 닫는다. 읽기 위험(1)을 막는 장치다
  - 파생 쓰기는 연산과 같은 트랜잭션(Outbox)에 넣거나, 리비전으로 늦은 쓰기를 거른다
  - 권한 알림은 Redis pub/sub(`perm:changed`, 03-ARCHITECTURE 5.5)
  - 완료 조건: 노드 2대 장애 실험(11-TEST-PLAN 13.2 의 노드 일시 정지와 리스, 노드 추가)
- 자세한 순서는 [IMPROVEMENT-ROADMAP.md](IMPROVEMENT-ROADMAP.md) 1번

### DC-2 세션 기록 상한과 오래된 baseRev (MEDIUM, 고침 #19)

- 문제: `ServerDocument.history` 와 `seenSeqs` 가 세션 수명 동안 줄지 않았다. `baseRev >= firstRev` 면 받아서, 아주 오래된 baseRev 의 묶음은 기록 전체와 변환하며 세션 스레드를 오래 잡았다
- 고친 것(D-06): 기록 창(기본 5,000)을 두고 창 밖은 버린다. 창보다 오래된 baseRev 는 `SubmitResult.Stale`(`ServerDocument.java:112`)이고 세션은 그 연결을 4011 로 닫는다. nack 를 보내면 그때 클라이언트가 편집을 버렸으므로 nack 대신 재접속(resume)으로 다시 맞추게 했다. 창 밖 순번의 재전송은 저장소의 `(client_id, client_seq)` 로 거른다
- 기존 생성자(창 없음)는 남겨 수렴 시뮬레이션과 벡터가 그대로 돈다
- 시험: `SyncScenarioTest`(창 크기 상한, 창 밖 baseRev 는 상태 불변의 Stale), `DocumentSessionTest`(창 밖 순번 재전송이 저장소 경로로 ack, 오래된 baseRev 는 nack 없이 4011)
- 재지 않은 것: 고치기 전의 메모리 증가와 CPU 점유는 재지 않았다

### DC-3 nack 와 rebase:false 에서 편집을 버림 (MEDIUM, 고침 #43)

- 문제: 서버가 묶음을 거부하거나, 변환 충돌이 나거나, 오래 떨어져 rebase:false 를 받으면 클라이언트가 그 묶음과 그 위의 입력을 통째로 버렸다(진단 시점 `clientSession.ts:143-150`, `collabClient.ts:226`)
- 고친 것(D-27)
  - 블록 단위로 살린다. 구조 편집(넣기, 나누기, 합치기, 옮기기, 지우기)이 섞이지 않은 블록의 글과 속성 편집만 떼어, 그 사이 확정된 남의 편집에 맞춰 변환하고 다시 적용한 뒤 새 묶음으로 보낸다
  - 다시 보내지 않는 경우: 거부 분류가 permission, input, empty(다시 보내도 거부된다. 권한 회수 뒤 편집은 남지 않아야 한다, D-20), 이미 한 번 살려 보낸 묶음이 다시 거부된 경우
  - 못 살린 글은 편집기 위 보관함에 "글 복사" 와 함께 보인다. rebase:false 의 대기 편집도 보관함으로 간다
  - 규약: nack 에 `code` 를 더했다(더하기만). code 가 없는 nack 는 다시 보내지 않는다
  - TS `ClientSession` 의 상태 기계 동작은 바꾸지 않았다(적합성 벡터 그대로). 살리기는 바깥(`salvage.ts`, `collabClient`)에서 한다
- 시험: `salvage.test.ts`, e2e(구조 충돌로 거부된 뒤에도 다른 블록에 친 글이 남고 두 화면이 수렴, 살리기를 끄는 변이에서 실패)
- 받아들인 위험: 살려 다시 보낸 글이 그사이 바뀐 문맥에서 뜻이 달라질 수 있다. 같은 블록의 남의 편집에는 변환으로 위치를 맞추므로 글자가 다른 블록에 가지는 않는다
- 남은 것: rebase:false 의 대기 편집을 복사본 페이지로 남기는 일(05-PROTOCOL 7.5)은 미뤘다

### DC-4 오프라인 저장 (LOW, 열려 있음)

연결이 끊긴 채 탭을 닫으면 보내지 못한 편집이 사라진다. IndexedDB 대기열(R-6, 10-FRONTEND 12.4)은 코드가 없다. 로드맵 4단계 항목이다.

### DC-5 순서 키 성장 (MEDIUM, 고침 #37)

- 문제(Node 22 측정): 맨 뒤 1,000번 추가에 키 167자, 맨 앞 1,000번에 200자. 서버는 키 길이를 검사하지 않았다
- 2단계 결정은 "정수부 가변 길이 키"(D-05)였다. 구현하면서 그 방식은 키 첫 글자의 뜻이 달라 지금 키와 섞을 수 없다는 것을 알았다. 그래서 같은 목표를 키 모양을 바꾸지 않고 이뤘다(D-24)
  - 첫 글자가 같은 키들 안에서 정해진 길이(가운데 'V' 에서 멀수록 1, 2, 3, 최대 4)로 하나씩 세고, 다 쓰면 첫 글자를 옮긴다
  - 키 모양(62진 소수, 0 으로 끝나지 않음)과 비교(문자열 순서)가 그대로라 옮기기(마이그레이션)가 필요 없다
- 결과(D-24 측정): 맨 뒤 1,000번 3글자, 10,000번 4글자, 1,000,000번 5글자. 예전 방식으로 길어진 'zzzzzV' 뒤에 1,000,000번 붙여도 10글자
- 서버는 블록 연산의 순서 키 모양과 길이(256)를 검사한다(`ChangePolicy.java:54, 186`)
- 시험: `FractionalIndexTest`(길이 상한, 예전 키 뒤와 앞, 섞어도 순서 유지), 적합성 벡터(TS 가 Java 와 같다. TS 의 최대 세는 길이를 바꾸는 변이에서 300건이 어긋난다), `ChangePolicyTest`
- 남은 한계: 같은 두 블록 사이에 1,271~1,525번 거듭 끼워 넣으면 256 에 닿고, 그 묶음은 nack 된다. 재균형 없이는 더 짧은 키를 만들 수 없어 받아들였다

### DC-6 블록 속성 검사 (LOW, 고침 #47)

- 고친 것(D-29): 허용 키는 type, level(1~3 정수), checked(참거짓), language(32자 이하). 다른 키는 거부한다. null 은 지우기라 받는다. 구분선은 결과 문서에서 글이 비어 있어야 한다
- 종류마다 허용 키를 나누지 않았다. 종류를 바꾼 뒤 예전 속성이 남은 문서가 이미 있어, 나누면 그 문서의 다음 편집이 거부된다
- 이미 저장된 문서는 다시 검사하지 않는다
- 시험: `ChangePolicyTest`
- 남은 것: 속성 값의 길이 한도가 서버 검사에 없다. 지금은 메시지 한도(64KB)가 상한이다(sendBudget.ts 주석, [남은 일](IMPROVEMENT-ROADMAP.md))

### DC-7 시험 공백 (LOW, 고침 #51)

- 무작위 생성기(`RandomOps`)에 이모지(서로게이트 쌍), 국기(코드 포인트 둘), 스무 번에 한 번 수백 낱자의 긴 글을 넣었다(D-31). 위치는 서로게이트 쌍 가운데를 자르지 않게 맞춘다(편집기가 그렇게 한다)
- `SnapshotReplayPropertyTest`: 무작위 연산 20~120 리비전을 커밋하면서 무작위 리비전에 스냅샷을 남기고, 스냅샷과 그 뒤 로그로 연 문서, 처음부터 재생한 문서, 메모리의 문서가 같은지 본다. 기본 15회. 스냅샷 뒤 첫 연산을 빼고 여는 변이에서 실패한다
- 다시 만든 적합성 벡터에는 파일마다 이모지 5만~254만 글자, 150자 넘는 글 488~21,636개가 들어 있고 TS 가 모두 같다

### DC-8 로그와 삭제 블록 정리 (LOW, 열려 있음)

연산 로그 90일 정리, 삭제 표시 블록 30일 정리(06-DATA-MODEL 8.3, 8.4)는 코드가 없다. 스냅샷은 3개만 남긴다. 버전 기록(V-1, V-2)과 함께 설계해야 한다. 로그를 정리하면 그 이전 시점으로 복원할 수 없기 때문이다.

| 커밋 하나가 묶음 N 개에 DB 왕복 2N+1 번 | DB 응답 200ms 지연에서 60개 묶음에 30.4초 | 중복 확인은 연결의 첫 묶음에서만, INSERT 문 하나(1,000 행까지) | D-38, #78 |

### D-38 의 순번 규칙을 따로 설명한다

중복 확인을 묶음마다 하지 않고 연결의 첫 묶음에서만 해도 되는 근거는 이렇다.

1. 이미 확정되었을 수 있는 묶음을 다시 보내는 경우는 재접속뿐이고, 그 묶음은 언제나 새 연결의 첫 묶음이다
2. 첫 묶음에서 "그 순번이 확정되었나" 와 "이 클라이언트의 가장 큰 확정 순번" 을 질의 하나로 읽는다
3. 그 뒤 한 연결의 순번은 늘기만 해야 한다. 늘지 않거나, 첫 묶음이 확정되지 않은 순번인데 더 큰 순번이 이미 있으면 그 연결만 4008 로 닫는다
4. 이 규칙이 없으면 유일 제약에 걸리는 묶음 하나가 INSERT 문 전체를 실패시키고, 세션을 버려 문서의 모든 연결이 끊긴다. 클라이언트 하나가 다른 사람의 편집을 끊을 수 있게 된다

정상 클라이언트(브라우저, Java `ClientSession`)는 이미 연결마다 순번을 늘리기만 한다. 같은 연결로 예전 순번을 다시 보내던 클라이언트만 영향을 받는다(05-PROTOCOL 7.5 의 5번).

- 1.4 의 "무작위 동시 편집 시뮬레이션 100만 회" 는 그 조건 그대로 돌리지 않았다. CI 는 `-Dcopage.ot.scale=10` 으로 수렴 시뮬레이션 15,000회(1,500 x 10, 회마다 클라이언트 2~5개, 40~199 걸음)와 TP1 묶음 쌍 1,000,000개(60,000 x 10 + 40,000 x 10)를 돌린다. 자세한 비교는 [PERFORMANCE-REVIEW.md](PERFORMANCE-REVIEW.md) 5장
- 노드 사이 네트워크 단절, 두 노드가 같은 문서를 든 경우의 실험은 노드가 하나라 하지 않았다
- 아주 오래 열린 세션의 메모리 사용량(DC-2 전후)은 재지 않았다
