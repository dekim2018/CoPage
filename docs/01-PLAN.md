# 코페이지(가칭) 기획서

실시간 공동 편집 문서 서비스의 목표, 기능 범위, 화면 흐름을 정리한다. 설계 문서는 02번부터 이어진다.

## 1. 프로젝트 개요와 목표

여러 사람이 한 페이지를 동시에 고쳐도 모두 같은 결과를 보게 되는 블록 기반 문서 서비스를 만든다. 동시 편집 충돌은 서버 주도 OT(Operational Transformation)를 Java로 직접 구현해서 푼다. 서비스 이름은 아직 정하지 않았고 이 문서에서는 가칭 코페이지(CoPage)라고 부른다.

### 1.1 이 프로젝트로 증명하려는 것

포트폴리오 구성에서 이 프로젝트가 맡은 역할은 "상태를 가진 실시간 서버"다. 팬파라이브가 MSA와 이벤트 흐름을 보여줬다면, 여기서는 아래 네 가지를 코드와 측정 수치로 보여준다.

1. 동시성 충돌을 락이나 덮어쓰기가 아니라 연산 변환 알고리즘으로 해결한 경험
2. 메모리에 상태를 든 서버를 여러 대로 늘리는 방법 (문서 세션 소유권, 문서별 노드 고정 라우팅)
3. 로그 기반 저장과 복구 (연산 로그 + 스냅샷, 특정 시점 복원)
4. 끊긴 연결에서도 깨지지 않는 정합성 (오프라인 편집, 멱등 재전송, 재접속 동기화)

### 1.2 확정된 결정

| 항목 | 결정 | 정한 날 |
| --- | --- | --- |
| 문서 모델 | 블록 기반 (노션 방식, 블록 트리) | 2026-11-22 |
| 동시성 제어 | 서버 주도 OT, Java 직접 구현 | 2026-11-13 |
| 서버 구조 | 모듈형 단일 서버, 같은 애플리케이션을 여러 대 실행 | 2026-11-22 |
| 확장 방식 | 문서별 노드 고정 라우팅 | 2026-11-13 |
| 저장 방식 | 연산 로그 + 스냅샷 | 2026-11-13 |
| 기능 범위 | 공유와 권한, 버전 기록과 복원, 댓글과 멘션, 워크스페이스와 페이지 트리 | 2026-11-22 |
| 주요 스택 | Java 25, Spring Boot 4.x, Spring Security, Vue 3 | 2026-11-22 |

### 1.3 하지 않는 것

범위를 지키기 위해 1차 개발에서 뺀 항목이다.

- 데이터베이스 뷰 (노션의 표, 보드, 캘린더)
- 표 블록, 이미지와 파일 업로드 (고도화 단계 후보)
- 모바일 앱 (모바일 브라우저에서 읽기와 간단한 편집만 확인)
- 결제와 요금제
- 종단 간 암호화, 서버 없는 P2P 동기화

### 1.4 성공 기준

아래 수치는 목표값이다. 13장의 부하 실험과 장애 실험을 돌린 뒤 실측값으로 바꿔 적는다.

| 지표 | 목표 | 측정 조건 |
| --- | --- | --- |
| 수렴 정확성 | 불일치 0건 | 무작위 동시 편집 시뮬레이션 100만 회 |
| 편집 확정 지연 (ack p99) | 150ms 이하 | 한 문서 동시 편집자 50명, 같은 리전 |
| 다른 사용자 화면 반영 지연 (p99) | 250ms 이하 | 위와 같은 조건 |
| 문서 열기 시간 (p95) | 500ms 이하 | 블록 2,000개 문서, 스냅샷 이후 연산 200개 |
| 노드 장애 후 편집 재개 | 10초 이내 | 소유 노드 강제 종료 |
| 확정된 연산 유실 | 0건 | 노드 강제 종료, 네트워크 단절 실험 |
| 노드 1대 수용량 | 열린 문서 500개, 연결 2,000개 | 4GB 서버, 힙 1GB |

## 3. 화면과 사용자 흐름

화면은 9개이고 편집기 화면 하나가 대부분의 시간을 차지한다. 색과 배치 같은 디자인은 구현 전에 시안을 따로 만들어 고른 뒤 반영한다.

### 3.1 화면 목록

| 화면 | 경로 | 주요 요소 |
| --- | --- | --- |
| 로그인, 가입 | `/login`, `/signup` | 이메일, 비밀번호 입력. 초대 링크로 들어오면 가입 후 해당 워크스페이스로 이동 |
| 워크스페이스 홈 | `/w/:workspaceId` | 왼쪽 사이드바(페이지 트리, 검색, 휴지통), 오른쪽에 최근 페이지 |
| 편집기 | `/w/:workspaceId/p/:pageId` | 제목, 본문 블록, 접속자 아바타, 연결 상태 표시, 공유 버튼, 댓글과 버전 기록 패널 열기 버튼 |
| 공유 대화상자 | 편집기 위 레이어 | 사용자 초대, 권한 변경, 링크 공유 켜기와 만료일 |
| 댓글 패널 | 편집기 오른쪽 | 열린 댓글, 해결된 댓글 탭. 댓글을 누르면 본문의 해당 위치로 이동 |
| 버전 기록 패널 | 편집기 오른쪽 | 시점 목록(시각, 편집자), 미리보기, 복원 버튼 |
| 검색 | Ctrl+K 레이어 | 검색어 입력, 결과 목록(제목, 일치한 본문 조각, 경로) |
| 알림 | 상단 종 아이콘 | 멘션, 댓글 답글, 초대 알림. 누르면 해당 위치로 이동 |
| 워크스페이스 설정 | `/w/:workspaceId/settings` | 멤버 목록, 역할 변경, 초대, 내보내기 |

링크 공유로 들어온 비로그인 사용자는 `/s/:shareToken` 으로 접속하고, 사이드바 없이 해당 페이지만 본다.

### 3.2 흐름 1: 두 사람이 같은 문단을 동시에 고친다

1. A와 B가 같은 페이지를 연다. 두 화면 모두 리비전 120에서 시작한다.
2. A가 문단 앞에 "안녕"을, B가 문단 끝에 "끝"을 거의 동시에 입력한다. 각자의 화면에는 자기 입력이 바로 보인다.
3. 서버에 A의 연산이 먼저 도착해 리비전 121이 된다.
4. B의 연산은 리비전 120을 기준으로 만들어졌으므로, 서버가 121번 연산에 맞게 위치를 변환한 뒤 리비전 122로 확정한다.
5. A는 122번을 받아 화면에 반영하고, B는 121번을 받아 자기 대기 연산과 맞춘 뒤 반영한다. 두 화면이 같아진다.

### 3.3 흐름 2: 지하철에서 연결이 끊겼다 돌아온다

1. 연결이 끊기면 상태 표시가 "오프라인"으로 바뀐다. 편집은 계속할 수 있다.
2. 보내지 못한 연산은 브라우저 저장소(IndexedDB)에 순번과 함께 쌓인다.
3. 연결이 돌아오면 마지막으로 확인한 리비전을 서버에 알리고, 그 사이에 다른 사람이 한 편집을 받는다.
4. 쌓아 둔 연산을 받은 편집에 맞게 변환한 뒤 순서대로 보낸다. 이미 서버에 들어간 연산을 다시 보내더라도 서버가 순번으로 중복을 걸러 낸다.
5. 끊긴 기간이 7일을 넘거나 그 사이 서버 연산이 5,000개를 넘으면 자동으로 합치지 않는다. 내 편집본을 "복사본" 페이지로 저장하고 원본은 서버 내용으로 연다.

### 3.4 흐름 3: 댓글 권한만 있는 사람이 의견을 남긴다

1. 소유자가 공유 대화상자에서 링크 공유를 켜고 권한을 "댓글"로 정한다.
2. 링크로 들어온 사람은 본문을 고칠 수 없고, 글자를 선택해 댓글만 달 수 있다.
3. 댓글을 달면 선택한 글자에 댓글 표시가 붙는다. 서버는 이 사람이 보낸 연산이 댓글 표시만 바꾸는지 검사하고, 글자를 바꾸는 연산은 거부한다.
4. 소유자가 링크 공유를 끄면 열려 있던 화면은 1초 안에 접근 불가 화면으로 바뀐다.
