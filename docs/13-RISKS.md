# 16. 위험과 미정 사항

가장 큰 위험은 편집기 어댑터이고, 0단계 2주 안에 계속 갈지 대안으로 바꿀지 판단한다. 어댑터는 0단계에서 통과해 계속 간다. 16.1 의 처음 여섯 줄은 계획할 때의 위험이고, 16.1.1 은 4단계 실험이 드러낸 위험과 그 처리다.

## 16.1 위험

| 위험 | 영향 | 대응 |
| --- | --- | --- |
| ProseMirror의 변화를 연산으로 바꾸는 과정에서 놓치는 경우가 생김 (붙여넣기, 한글 조합, 여러 블록 삭제) | 화면과 서버 문서가 어긋난다 | 0단계에서 먼저 검증한다. 어댑터가 만든 연산을 확정 문서에 적용한 결과와 편집기 문서를 개발 모드에서 매번 비교한다. 다르면 바로 오류를 낸다 |
| split과 merge의 변환 규칙에 빠진 경우가 있음 | 특정 순서에서 문서가 갈라진다 | 속성 테스트와 수렴 시뮬레이션을 1단계 완료 기준으로 둔다. 통과 전에는 서버를 만들지 않는다 |
| 두 언어 구현이 미묘하게 다름 (문자열 길이, 정렬 순서, 숫자 처리) | 클라이언트만 어긋난다 | 적합성 벡터를 CI에서 매번 돌린다. 클라이언트가 주기적으로 문서 해시를 서버와 비교해 다르면 다시 받는다. 해시 비교는 아직 없다 |
| 거부율이 예상보다 높음 | 입력이 자주 취소되어 쓰기 불편하다 | 사유별 거부율을 재고(`collab.nack`), 가장 잦은 사유부터 변환 규칙으로 옮긴다. 거부된 묶음에서 다른 블록의 글은 살려 다시 보내고, 못 살린 글은 보관함에 보인다(D-27) |
| 24주 안에 범위를 다 못 함 | 측정과 문서화가 빠진다 | 14.2의 순서로 줄인다. 측정 단계는 남긴다 |
| 4GB 서버에서 노드 2대와 DB가 메모리 부족 | 시연 중 종료 | 팬파라이브의 메모리 예산 방식(컨테이너별 상한, 측정 스크립트)을 가져온다. 노드 한 대는 힙 1GB 로 연결 2,000개를 버텼다(노트북). 4GB 서버 전체 구성은 아직 재지 않았다 |

### 16.1.1 실험이 드러낸 위험

| 위험 | 드러난 곳 | 처리 | 남은 것 |
| --- | --- | --- | --- |
| 연결이 늘면 WebSocket 글 버퍼가 힙을 넘침 | 문서 500 x 4명 부하에서 연결 약 930개에 OutOfMemoryError | 버퍼를 메시지 한도와 같게(연결당 약 512KB → 131KB). 연결 2,000개가 힙 1GB 에서 돈다 (D-36) | 연결이 목표를 넘으면 부분 메시지를 직접 모으는 방식을 다시 본다 |
| DB 왕복 시간에 처리량이 묶음 수만큼 비례해 떨어짐 | DB 응답에 200ms 를 더한 실험에서 초당 2.0개 | 연결별 순번 규칙과 INSERT 하나로 왕복을 한 번으로. 초당 8.6개 (D-38, ADR 0016) | 왕복 한 번은 남는다. DB 가 멀리 있으면 그만큼 ack 가 늦다 |
| DB 가 답하지 않으면 문서 세션이 영영 멈춤 | PostgreSQL 일시 정지 실험(40초 넘게 대기) | 소켓 시간 한도 10초, 묶음 처리 중 저장소 실패도 세션 버리기 (D-33) | 한도 동안(최대 10초) 그 문서의 편집이 멈춘다 |
| 빠른 타이핑이 서버 빈도 한도에 걸려 편집기가 멈춤 | CI e2e 간헐 실패(#54) | 클라이언트가 묶음을 50ms 에 하나만 보낸다 (D-34) |  |
| 64KB 를 넘는 붙여넣기에 편집기가 멈춤 | 규약은 나눠 보낸다고 했지만 코드가 없었다 | 클라이언트가 60,000 바이트 안의 묶음으로 나눈다 (D-37) | 서버 한도를 클라이언트가 모른다. 서버 한도를 60,000 보다 작게 줄이면 안 된다 |
| Redis 장애가 노드 재시작으로 번짐 | 묶은 health 가 Redis 를 본다 | 생존 검사는 liveness 만 쓴다 (D-25, ADR 0014) | 배포 설정에서 지켜야 한다(7단계) |
| 다중 노드에서 두 노드가 같은 문서를 씀 | 아직 다중 노드가 없다 | 설계상 `(doc_id, rev)` 기본 키가 늦게 쓴 쪽을 실패시킨다 (ADR 0013) | 리스, 양도, 노드 사이 권한 변경 전달이 없다. 다중 노드 실험(일시 정지, 노드 추가)과 노드 넘김의 재개 시간을 아직 재지 않았다. 지금 가장 큰 남은 위험이다 |
| 권한 변경이 다른 노드의 열린 연결에 닿지 않음 | 설계 (D-17) | 노드 1대에서는 1초 안에 적용된다 | 4단계에서 Redis pub/sub 으로 넓힌다 |
| 브라우저를 닫으면 보내지 못한 편집이 사라짐 | IndexedDB 가 없다 | 재접속까지는 메모리 buffer 로 지킨다 | R-6, 4단계 |

## 16.2 정해야 할 것

- [ ] 서비스 이름 (지금은 가칭 코페이지)
- [ ] 시작일. 정해지면 14장의 주차를 날짜로 바꾼다
- [ ] 이미지와 파일 업로드를 고도화에 넣을지
- [ ] 소셜 로그인(A-4)을 할지, 한다면 구글과 깃허브 중 어느 쪽인지
- [ ] 화면 디자인 시안 (키 컬러, 사이드바와 편집기 배치, 커서 12색)
- [ ] 링크 공유로 들어온 비로그인 방문자에게 편집까지 허용할지, 댓글까지만 허용할지

## 16.3 착수 첫 주에 확인할 것

- [x] jqwik이 Spring Boot 4.1의 JUnit 버전에서 동작하는지 (쓰지 않기로 했다. 4장 참고)
- [ ] pg_bigm이 PostgreSQL 17에서 빌드되는지 (검색, 5단계 전에)
- [ ] Caddy의 URI 해시 정책이 노드 추가 시 문서를 얼마나 다시 배치하는지. 많이 바뀌면 HAProxy의 consistent 해시로 바꾼다
- [x] Spring Boot와 Tiptap의 최신 패치 버전 (Spring Boot 4.2.0, Tiptap 3.35.0. 이후 갱신은 Dependabot 이 연다)
