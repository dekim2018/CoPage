# ADR 0016. 커밋은 연결별 순번 규칙과 INSERT 문 하나로 DB 왕복을 한 번으로 한다

- 상태: 확정
- 결정일: 2026-11-24
- 관련 문서: [03-ARCHITECTURE.md](../03-ARCHITECTURE.md) 5.2.1, [05-PROTOCOL.md](../05-PROTOCOL.md) 7.5, [06-DATA-MODEL.md](../06-DATA-MODEL.md) 8.2, [review/DECISIONS.md](../review/DECISIONS.md) D-38

## 고른 것

- 한 연결에서 `clientSeq` 는 늘기만 해야 한다. 저장소의 중복 확인은 연결의 첫 묶음에서만 한다. 그 순번의 확정 여부와 이 클라이언트의 가장 큰 순번을 질의 하나로 읽는다. 규칙을 어기면 4008 로 닫는다.
- 한 차례에 모인 묶음을 `INSERT ... VALUES (...), (...)` 문 하나로 넣는다. 1,000행이 넘으면 나눠 한 트랜잭션에 넣는다.

## 버린 대안

- 묶음마다 중복 확인 SELECT 와 INSERT 를 보내고 COMMIT 한다(예전 방식, 왕복 2N+1 번).
- JDBC batch(`reWriteBatchedInserts`). pgjdbc 설정에 기대고 BEGIN/COMMIT 왕복이 남는다.
- `unnest` 배열 INSERT. 문장은 고정되지만 jsonb 배열 변환이 번거롭다.
- 중복 확인을 묶음 전체에 한 번(IN 목록). 왕복은 한 번 남고, 연결별 규칙이 없으면 아래의 커밋 실패를 막지 못한다.
- 중복 확인을 아예 빼고 유일 제약에 맡긴다.

## 이유

- 다시 보내는 묶음(이미 확정되었을 수 있는 것)은 언제나 재접속한 연결의 첫 묶음이다. 그 뒤로는 확정된 순번이 다시 올 수 없다.
- 유일 제약 `(doc_id, client_id, client_seq)` 에 걸리는 묶음이 하나라도 섞이면 묶음 커밋 전체가 실패하고 세션을 버린다. 클라이언트 하나가 문서의 모든 연결을 끊을 수 있다. 순번이 늘기만 하는 규칙과 첫 묶음의 최대 순번 확인이 그 경우를 막는다. 그래서 중복 확인을 그냥 뺄 수 없다.
- 문장 하나는 자동 커밋에서도 원자적이라 BEGIN/COMMIT 이 필요 없다. 묶음 크기와 상관없이 왕복이 한 번이다.

## 감수하는 것

- 규약이 조금 강해졌다. 같은 연결로 예전 순번을 다시 보내던 클라이언트는 4008 로 끊긴다. 화면 클라이언트와 Java `ClientSession` 은 이미 그렇게 보내지 않는다.
- INSERT 문이 행 수에 따라 달라져 문장 준비를 다시 쓰지 못한다.

## 확인

DB 응답마다 200ms 를 더한 `DbLatencyTest` 에서 60개 묶음이 30초 남짓(초당 2.0)에서 7.0초(초당 8.6)가 되었다. 로컬에서 한 문서 100명의 ack p99 가 125.8ms 에서 47.2ms 가 되었다.

## 다시 검토할 조건

다중 노드에서 한 클라이언트가 같은 문서에 두 연결로 동시에 보내는 경우가 생기거나, INSERT 문 하나의 크기가 문제가 되면 이 문서를 고치고 상태를 "대체됨"으로 바꾼다.
